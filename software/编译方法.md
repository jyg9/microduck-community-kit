# 编译方法

`microduck_feetech` 是官方 [microduck](https://github.com/pollen-robotics/microduck) 的飞特舵机
（FeeTech SCS/HLS）适配版源码。本文只讲**工具链与流程**：怎么编译、怎么测试、怎么装到机器人上。
协议具体改了什么、上车要注意什么，见 [`microduck_feetech/FORK.md`](microduck_feetech/FORK.md)
与[补丁说明](../firmware/v1/patches/microduck_feetech_patch.md)。

- 编译机：x86_64 Linux
- 目标板：Radxa ZERO 3 / 3W（RK3566，aarch64），Armbian

## 一、两条循环，别混用

改动分两类，用两条不同的循环最快。

### 1. 本机测试循环（秒级，不需要板子）

飞特帧的编解码、坐标/速度/电流的符号-幅值换算、增益标度都在 `duck-control` 里，本机就能测：

```bash
cd software/microduck_feetech

cargo test -p duck-control      # 总线协议与控制
cargo test -p robotd-params     # 参数默认值（含增益）
```

首次要为本机编译依赖（约一分钟），之后增量重跑在秒级 —— 改一行、测一下的成本极低，
改总线逻辑应该尽量停在这一层。

> ⚠️ **本机循环不要导出交叉编译的 `PKG_CONFIG_*` / `RUSTFLAGS`**（见第三节）。
> 它们会把 aarch64 的库路径塞进 x86 链接，让本机测试直接失败，报错却指向无关的地方。

### 2. 交叉编译并上车（分钟级）

一次性准备交叉工具链：

```bash
cargo install cargo-zigbuild --locked
```

另需系统安装 [zig](https://ziglang.org/download/)。之后每次迭代：

```bash
export DUCK_DEV_SECRET_KEY=/path/to/your.dev.key     # 见第四节
export DUCK_BOARD_USER=<板子上的登录用户>
scripts/dev-push.sh <user>@<board-host>
```

`scripts/dev-push.sh` 依次做：交叉编译 → 打包成发布产物 → 签名 → `scp` 到板子 →
通过 `robotctl update apply --from` 应用 → 走健康门 → 校验每个守护进程都在跑新版本。

耗时的大头是「改动的 crate 及其下游重编译 + 重新链接」（改 `duck-control` 约 40 秒），
打包、传输与切换再占一到两分钟。全部缓存命中的空跑在 1 秒内。

只做预检、**不切换**（验签、哈希、兼容性、单元检查全都会跑，但不移动 `current`，
不重启任何守护进程）：

```bash
scripts/dev-push.sh --dry-run <user>@<board-host>
```

`--dry-run` 也会把产物复制到板子上，所以它会覆盖板子上的待装目录；正式推送会再覆盖一次。

板子上的运行版本：

```bash
robotctl version          # 同时报告「已安装」与「正在运行」，两者短暂不一致是正常的
robotctl health
```

## 二、依赖下载（网络受限时）

日常迭代**不需要联网**：依赖与 sysroot 都缓存好之后，交叉编译可以完全离线完成。

```bash
cargo board --bins --offline     # 零网络
```

只有两种情况需要下载：**新增/升级依赖**，以及**重建 sysroot**。如果所在网络访问
`crates.io` 或 `deb.debian.org` 很慢甚至连不上，各配一个镜像即可。

### crates.io

任选一个可达的镜像，写进 `~/.cargo/config.toml`（或 `$CARGO_HOME/config.toml`）：

```toml
[source.crates-io]
replace-with = "rsproxy-sparse"

[source.rsproxy-sparse]
registry = "sparse+https://rsproxy.cn/index/"
```

source replacement 是 cargo 的官方机制，`Cargo.lock` 里记录的仍是标准的 `crates.io` 源，
不会污染锁文件。国内可选的镜像还有清华 TUNA、中科大 USTC 等（注意有些只镜像索引、
不镜像 crate 文件，配之前先看它的 `config.json` 里 `dl` 指向哪里）。

### Debian 包（sysroot）

`scripts/cross-sysroot.sh` 的下载源可以用环境变量换掉：

```bash
export DUCK_DEBIAN_MIRROR=https://mirrors.aliyun.com/debian   # 默认 http://deb.debian.org/debian
```

直连与国内镜像的差距是数量级的（实测 60 KB/s 对 7 MB/s），换个镜像能把 sysroot 的
构建从「几十分钟」压到「一分钟」。

> GitHub 的 `raw.githubusercontent.com` 在部分网络下不可达。它只在**首次给板子做
> provisioning**（`scripts/provision-board.sh`）时用到 —— 日常编译与 dev-push 不碰它。
> 需要时自备代理即可。

## 三、交叉编译与 sysroot

交叉目标定义在 `microduck_feetech/.cargo/config.toml`：

```
cargo board  =  zigbuild --release --target aarch64-unknown-linux-gnu.2.31
```

`.2.31` 是 glibc 下限（cargo-zigbuild 的语法）。**这个下限不能省**：不pin 的话会链接到
编译机自己的 glibc，在编译机上一切正常、到板子上直接起不来，而构建输出里没有任何提示。

`mediad` 依赖 GStreamer，`padd` 依赖 libudev，所以交叉链接需要一份目标平台的 sysroot。
`scripts/cross-sysroot.sh` 从 Debian trixie 的 arm64 仓库取需要的 `-dev` 包，解到本地：

```bash
export DUCK_SYSROOT=/path/to/sysroot          # 可选，默认为临时目录下的路径
eval "$(bash scripts/cross-sysroot.sh | grep '^export')"
cargo board --bins
```

它导出的四行是：

| 变量 | 作用 |
|---|---|
| `PKG_CONFIG_SYSROOT_DIR` | 让 `pkg-config` 把路径前缀到 sysroot |
| `PKG_CONFIG_LIBDIR` | 只在 sysroot 里找 `.pc`，不回落宿主机的 |
| `PKG_CONFIG_ALLOW_CROSS` | 允许交叉查找 |
| `RUSTFLAGS` | 给链接器加 `-L <sysroot>/usr/lib/aarch64-linux-gnu` |

`scripts/dev-push.sh` 自己会做这一步，所以**推送时不用手工导出**；只有手工跑
`cargo board` 时才需要。

> ⚠️ **sysroot 的路径会进入 `RUSTFLAGS` 指纹**。也就是说换个 `DUCK_SYSROOT` 位置
> 会导致**全量重编译**。想挪位置的话，一次挪好，别反复搬。

`--check` 只校验 sysroot 里的模块是否齐全，不下载、不导出，适合排查环境问题：

```bash
bash scripts/cross-sysroot.sh --check
```

## 四、打包与签名

板子的更新器**强制验签**：产物必须由一个板子信任的密钥签名，否则拒绝安装。
所以「编译出来直接拷进去」是行不通的。

### 拿密钥的三条路

1. **团队成员给的 `team.dev.key`**（官方开发流程，CI 用它签分支构建）。
2. **只用正式 release**，不改代码。
3. **自建一套密钥** —— 复刻/自定义机器人通常走这条，用仓库自带的 `xtask`：

```bash
cargo run -p xtask -- keygen --kind dev --name <name> --out <dir-outside-repo>
# 生成 <name>.dev.pub 与 <name>.dev.key
```

`keygen` 会拒绝把私钥写进仓库内，这是刻意的：私钥一旦提交就无法撤回。

### 让板子信任它

两个条件**都要**满足，少一个都会在安装时报「签名无法验证」，而错误信息读起来像产物损坏：

```bash
# 在板子上，公钥文件名必须以 .dev.pub 结尾 —— 这个后缀才是「dev key」的分类依据
sudo cp <name>.dev.pub /etc/robot/trusted_keys/<name>.dev.pub
sudo chmod 644 /etc/robot/trusted_keys/<name>.dev.pub

# allow_dev_keys 必须为 true
grep -n 'allow_dev_keys' /etc/robot/updater.toml     # 期望 allow_dev_keys = true

sudo systemctl restart updaterd
```

只做其中一半（比如装了公钥但 `allow_dev_keys` 还是 `false`）会留下一个仍然拒绝 dev 构建的板子。
自建的 dev 公钥让这块板子信任你签名的任何东西，**只对开发板这样做**。

校验「这台板子确实是 dev board」：

```bash
grep -c 'DEV BOARD' /var/lib/robot/provision.log     # 期望 1
```

### 打包

`scripts/dev-push.sh` 负责把二进制、systemd 单元、hooks 与配置打成一个 `.tar.zst`
（`cargo xtask package`），再用 `cargo xtask sign` 签名。产物落在 `dist/`，包含
`manifest.json`、artifact 以及各自的 `.minisig`。

版本号由 `git rev-parse` 与时间戳生成（形如 `<版本>-dev.local.<epoch>.g<sha>`），
所以同一棵脏树连着推两次也不会互相覆盖。

## 五、装到板子上

`dev-push` 的最后一跳就是这条命令，也可以手工用：

```bash
sudo robotctl update apply daemon --from <目录>
```

`<目录>` 里要有 manifest、签名和 artifact。路径**不能放在 `/tmp` 或 `/var/tmp`**：
`updaterd.service` 设了 `PrivateTmp=yes`，它有自己的一份 `/tmp`，它看到的是空的。
`dev-push` 默认用板子上的家目录下的 `duck-sideload`。

带健康门与自动回滚，出问题会自己退回上一版。手工回滚：

```bash
sudo robotctl update rollback daemon
```

### 几个边界情况

- **板子上的 `updaterd` 太旧**（早于 `apply --from` 所需的 API 版本）：加 `--bootstrap`，
  它会停掉 `robotd` 并让过这一次的健康门。之后照常用普通命令。
- **本地构建的版本号比板子上装的低**是正常的（dev 版带 prerelease 后缀，排序天然靠后）。
  通过 `--from` 安装**不受降级保护限制**，这是刻意的：本地目录是操作员的明确意图，
  不是「镜像回退了」。而走网络通道的更新是受保护的。
- **`robotd` 报 `degraded: no robot on the motor bus`** 不一定是安装失败。舵机没上电、
  总线没接都会这样，日志会说明是哪一种；上电后 `robotd` 自己会恢复，不需要重装。

## 六、常见报错

**`can't find bin 'duck-bench' at path .../duck-detect/src/bin/duck-bench.rs`**
（或 `pet-detect/src/bin/*.rs`）—— 源码文件不在。根目录与 `software/` 下的 `.gitignore`
套用了通用多语言模板，其中 `bin/`、`*.d`、`*.bin` 三条对一个 Rust + 固件仓库过宽，
会按**目录名**匹配、连源码目录一起排除。本仓库已修正（并恢复了一次被它们吃掉的
`sysusers.d/`、`journald.conf.d/`、`src/bin/`、`robotctl/assets/duck.bin`）。
clone 下来先确认这些文件在。

**`Install a sysroot for the target platform and configure it via PKG_CONFIG_SYSROOT_DIR ...`**
—— 手工跑 `cargo board` 时没导出第三节那四行。`dev-push.sh` 不会有这个问题。

**`pkg-config` 找不到某个模块** —— 用 `cross-sysroot.sh --check` 看缺哪个，它会把模块名
和实际版本列出来。Debian 的包名会随发行版改名（例如 trixie 把 GLib 的头文件拆了、
`libglib2.0-0` 改名成 `libglib2.0-0t64`），脚本里的包列表要跟着改。

**`cargo-zigbuild is not installed`** —— `cargo install cargo-zigbuild --locked`，另需 zig。

**板子上 `mediad` 反复重启** —— 看 `journalctl -u mediad -b`。常见原因是相机型号与
overlay 不匹配（例如默认按 imx219 装配，而实际装的是别的模块），与总线改动无关。
没有相机时它也会退出。

## 七、上车前的实机确认

编译通过 ≠ 车上能用。以下三件事**必须**自己确认为准（依据见
[FORK.md](microduck_feetech/FORK.md) 与[补丁说明](../firmware/v1/patches/microduck_feetech_patch.md)）：

1. **增益要按关节重新整定。** 默认值已按飞特标度改过，但只有**悬空、无负载**的台面证据；
   负载下的稳定裕度、站立与起步手感都要重测。`software/hls_servo_debugger` 初始化时写的
   是同一组寄存器，两处的值要保持一致。
2. **同一串口只能有一个进程持有。** `robotd` 用 `TIOCEXCL` 打开端口，但它拦不住**已经**
   打开的同名 fd —— 调试器先占着串口时，两个进程会各读走一半字节，现象是每个 tick 随机
   丢几个舵机、看起来像节点坏了。上车前用 `fuser <串口设备>` 确认只有 `robotd`。
3. **关节零点与正方向、速度/电流的绝对标度仍未实机核对。** 收养新舵机（改 ID）是破坏性
   操作，建议先用备用舵机验证。
