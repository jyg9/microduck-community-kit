# imu_to_dxl v1 通信协议参考（外部主机实现者版）

本文是 `imu_to_dxl` v1 节点的**自包含**通信协议参考，面向用任意语言自行实现主机/主站
（master）的外部开发者。读完本文即可实现：读遥测、读写配置、触发动作、以及**通过同一条
电机总线给节点升级固件**。

文中所有数字、地址、位域、操作码与常量都标了出处：源码用 `文件:行`（例如 `src/board.h:301`），
设计文档用 `文档 §节`。**没有出处、又无法从仓库确认的值，一律不写，集中列在 §15.5
「未在仓库中找到」**。标注约定：

* **【实测】** = 在真硬件上量到的数字（真实舵机 / 本节点 / 真 PCBA）。
* **【设计】** = 固件里定死的设计值或设计选择，不是测量结果。
* **【源码】** = 直接读代码得到的事实。
* **【估算】** = 由实测常数推算，不是直接测量。

**固件版本见 §13**（注意：节点寄存器里报的固件版本与
升级镜像头里的版本号不是同一个数，见 §13.1）。

## 1. 概览

### 1.1 节点是什么

`imu_to_dxl` v1 是一块 **GD32F303CC**（LQFP48，256 KB Flash / 48 KB SRAM，12 MHz 晶振 →
120 MHz，`src/board.h:5-6`）节点板。它把一个 **20 字节的 IMU 数据块**发布成**伺服总线上的一个
从站**，让主机在同一次总线上同时读到姿态与全部舵机状态（`README.md:1-5`）。

真实机器人上的拓扑（`README.md:11-15`、`docs/bus_timing_borrow_plan.md:346-353`）：

* 节点与 **15 颗 FeeTech HD-1910-C001** 舵机（ID `10-14`、`20-24`、`30-34`）**并联**在
  同一条 **1 Mbps 半双工**伺服总线上；
* 节点 ID = **200**；
* 主机（PC / 机器人主控）经 **USB 串口适配器**接到这条总线；
* 节点使用与舵机**相同的总线电气层与帧格式**，所以总线上其它舵机看到的只是"发给 ID 200 的
  普通读写"，主机不需要为舵机加任何特殊逻辑（`docs/upgrade.md:196-199`）。

节点是**从站**：它**只应答，从不主动发送**（【源码】唯一的发送路径都来自收到并解析出一帧之后，
`src/bus.c:126` 与 `src/bus.c:275`；主循环的 `bus_poll()` 只负责把"等自己应答槽"的延迟应答发出去，
`src/bus.c:262-282`）。

### 1.2 两种协议人格，一条总线

节点在**同一个物理端口**上同时实现了两套协议，按帧的**第 3 个字节**自动识别
（`src/bus.h:13-17`）：

| 人格 | 协议 | 帧头 | 校验 |
|---|---|---|---|
| **Dynamixel 2.0** | ROBOTIS Protocol 2.0 | `FF FF FD 00` | CRC-16（整帧，含帧头） |
| **FeeTech SCS/HLS** | 飞特 SCS/HLS（HD-1910 系列） | `FF FF <ID>` | `~SUM`（8 位取反和） |

两套协议共用同一个节点 ID（默认都是 200）与**同一组遥测/配置语义**，但**地址映射不同**
（Dynamixel 跟随 XL330 控制表，FeeTech 跟随 HLS 内存表），见 §7。

### 1.3 主机能用它做什么

| 能力 | 手段 | 章节 |
|---|---|---|
| 读遥测（陀螺 / 四元数 / 加速度 / 计数 / 状态位） | `READ` / `SYNC_READ` | §6、§11 |
| 与 15 颗舵机一次 `sync_read` 读完 | FeeTech 地址 56、长度 **15** | §6.2 |
| 与 15 颗舵机一次 **`fast_sync_read`（`0x8A`）**读完（Dynamixel 路线，省掉每台的帧头与转向） | `0x8A`，ID 列表把本节点放第 0 位；应答是一个 `ID=0xFE` 的聚合帧 | §3.2.1、§11(c2) |
| 读/写配置（ID、波特率、安装系、陀螺偏置、模拟模式、调试级别、协议锁） | 厂商配置窗（DXL 148 / Fee 160，20 字节） | §8 |
| 触发动作（保存配置、恢复出厂、重启、重启融合、确认 trial 镜像、切槽、进 bootloader） | 厂商窗 `V_CMD` 命令 1~7 | §8.4 |
| 识别固件状态（应用 / bootloader、槽、版本、镜像 CRC、trial 状态） | 身份窗（180..195，只读） | §9 |
| **通过同一条总线升级固件** | 升级会话窗（208..255）+ `.ipkg` 包 | §10 |

## 2. 物理层与总线参数

| 项目 | 值 | 出处 |
|---|---|---|
| 总线 | 单线**半双工**，所有节点并联；任意时刻只能有一个发送方 | `飞特通讯协议说明.md §1` |
| 电平 | TTL 3.3 V | `飞特通讯协议说明.md §1` |
| 帧格式 | **8N1**（8 数据位、无校验、1 停止位），无流控 | 【源码】`src/uart_port.c:99-101`；`飞特通讯协议说明.md §1` |
| 默认波特率 | **1 Mbps**（Dynamixel 码 3 / FeeTech 码 0） | `src/board.h:308-317`；波特率表 `src/dev.c:592-605` |
| 节点主总线 | USART1，PA2 = TX / PA3 = RX | `src/board.h:21-23`、`src/board.h:352-355` |
| 调试口 | USART0，PB6 = TX / PB7 = RX；**只输出 DBG_ 日志**（115200），不应答协议帧。`BUS_MIRROR_ENABLE=1`（台架实验构建，默认 **0**）才把它也当第二协议端口；**即使打开，升级会话在那边仍被拒绝**（§10.2） | `src/board.h:30-31,62-75,310-311`、`src/bus.c:213-241` |
| 方向控制 | **硬件自动方向**：原理图里 `TXD_EN` 由 TX 直接产生（Q1 + R28/R29/C22），固件不控制任何 GPIO | `src/board.h:21-23`、`README.md:78` |

要点：

1. **半双工单线，同一时刻只有一个发送方。** 主机必须严格按照"一帧请求 → 等应答（或超时）
   → 下一帧"的节奏；不要流水式连发（`docs/upgrade.md` 的升级流程、`src/bus.c:262-282` 的
   请求-应答结构都依赖这一点）。
2. **自动方向缓冲把主机的 TX 变成总线驱动**，主机侧必须使用支持 1 Mbps 且方向自动切换的
   半双工/USB-TTL 适配器；台面用的是 CH340（`docs/upgrade.md:305`、`docs/bus_timing_borrow_plan.md:63`）。
3. **节点能听到自己的发送**（半双工回声）。固件在发送期间以及发送完成后一个**按波特率计算的
   时间窗**（`UART_ECHO_WINDOW_BYTES = 3` 个字节时间，1 Mbps 下 ≈30 µs）内丢弃收到的字节
   （`src/uart_port.h:22-34`、`src/uart_port.c:26-38,251-253`）。主机不需要知道这个窗口，但
   应当知道节点在应答后极短时间内可能收不到紧随的字节——现实中主机下一帧至少是毫秒级，
   远在窗口之外。
4. **节点上电后立即可应答**：文档给出的验收目标是上电 ≤ 50 ms 内可应答（`docs/bus_timing_borrow_plan.md:423`），
   **但这一项尚未实测**（同处标注"未测"），所以不要把它当成保证，见 §15.5。
5. 本文只描述**电机总线**。USART0 是**调试口**：只输出 DBG_ 日志，默认不解析任何帧
   （`BUS_MIRROR_ENABLE = 0`）；台架实验构建把它也当协议口，但**升级会话在那里一律被拒**
   （§10.2）。调试文本行以 `#` 开头，ASCII 里没有 `0xFF`，所以即使两个口接在同一台 PC 上
   也不会被误认成帧（`src/dbg.c`）。

## 3. 帧格式与协议识别

### 3.1 Dynamixel 2.0 指令帧（主机 → 节点）

与 rustypot 1.6 / ROBOTIS Protocol 2.0 逐字节一致（`src/dxl2.h:8-11`、`docs/dynamixel_slave.md:14-20`）。

| 偏移 | 字节数 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `0xFF` | 帧头 |
| 1 | 1 | `0xFF` | 帧头 |
| 2 | 1 | `0xFD` | 协议 2.0 标识（**也是协议自动识别的判据**，见 §3.8） |
| 3 | 1 | `0x00` | 保留 |
| 4 | 1 | `ID` | 目标 ID（`0xFE` = 广播，`src/board.h:380`） |
| 5 | 1 | `LEN_L` | 长度低字节 |
| 6 | 1 | `LEN_H` | 长度高字节 |
| 7 | 1 | `INST` | 指令码（§5.1） |
| 8 | `N` | `PARAM...` | 参数（**已做字节填充**，见 §3.4） |
| 8+N | 1 | `CRC_L` | CRC-16 低字节 |
| 9+N | 1 | `CRC_H` | CRC-16 高字节 |

* **`LEN = len(参数) + 3`**（3 = INST + 2 字节 CRC），**整帧 = 7 + LEN**（`src/dxl2.c:179-180`、
  `host/bus.py:213-222`）。
* `LEN` 统计的是**填充后**的参数长度（`host/bus.py:220`）。
* 节点收帧时先按 `LEN` 收满整帧，再校验 CRC，再对 `f[8 .. LEN-3]` 去填充
  （`src/dxl2.c:570-597, 107-114`）。

### 3.2 Dynamixel 2.0 状态帧（节点 → 主机）

| 偏移 | 字节数 | 字段 | 说明 |
|---|---|---|---|
| 0..3 | 4 | `FF FF FD 00` | 帧头 |
| 4 | 1 | `ID` | 本节点 ID（恒为本机 ID，即使收到的是广播 PING） |
| 5..6 | 2 | `LEN_L LEN_H` | 长度，**统计填充后的字节** |
| 7 | 1 | **`0x55`** | **状态标记**：指令帧这里是 `INST`，状态帧这里是固定值 `0x55`（`src/board.h:385-386`） |
| 8 | 1 | `ERR` | 错误位（§5.3） |
| 9.. | `n` | `PARAM...` | 参数（**已填充**） |
| 末 2 | 2 | `CRC_L CRC_H` | CRC-16 |

* **`LEN = 1(标记) + 1(ERR) + len(参数) + 2(CRC)`**，无填充时 = `len(参数)+4`；整帧 = `7 + LEN`
  （`src/dxl2.c:53-55`、`docs/dynamixel_slave.md:25-28`）。
* 状态帧的 **`ERR + PARAM`（即body）整体被字节填充**，`LEN` 与 CRC 都按填充后的样子计算
  （`src/dxl2.c:22-24,50-70`）。主机必须在 **CRC 校验通过之后**才去填充
  （`host/bus.py:269-274`）。

#### 3.2.1 Fast Sync Read（`0x8A`）的聚合状态帧

`0x8A` 的**指令帧与 `0x82` 逐字节相同**（只换 opcode：`src/board.h:416`），不同在应答：
所有被点名的设备**共同拼出一个**状态帧，`ID` 是广播 `0xFE`：

| 发出者 | 字节 |
|---|---|
| ID 列表**第 0 台**设备（只有它发） | `FF FF FD 00 FE LEN_L LEN_H 0x55` |
| 每台被点名的设备，按 ID 列表顺序 | `ERR ID DATA(X) CRC_L CRC_H` |

规则（【外部】ROBOTIS protocol 2.0 手册 "Fast Sync Read (0x8A)"；【源码】`src/dxl2.c:75-171`
与 `src/dxl2.c:373-434`；【实测】§11(c2)）：

* **`LEN = 1(标记) + N × (X + 4)`**，`N` = ID 列表长度，`X` = 指令里的读长。它**覆盖整包**，
  不是本机那一段：16 台设备各读 12 字节 → `LEN = 257`，整帧 264 字节，而本节点只发 24 字节。
* 每段的 `ID` 是**设备自己的 ID**（不是 `0xFE`）；`ERR` 是它自己的错误位（§5.3）。主机按 ID
  列表顺序逐段取数，段的 ID 与请求不符即整包无效。
* **每段末尾的 CRC 覆盖"从头到本段数据末尾"**（含前面所有段和 8 字节前缀）。主机因此可以逐段
  校验，这也正是"段的位置对不对"的判据；**最后一台的 CRC 就是整包的 CRC**（`0x82` 那种单帧
  校验器用 `LEN` 切出整包后照样能过 `dxl_parse_status`，但它看到的是原始各段字节）。
* **不做字节填充**：数据里出现 `FF FF FD` 时原样发出，主机必须按 `LEN` 定长切分（官方 SDK 读
  这类包时明确跳过去填充，rustypot 同样按 `LEN` 切）。§11(c2) 有反证向量。
* **"轮到自己"的判据是字节数，不是时间槽**：本机排在第 k 位时必须等到前面 k 段上线才能算出
  自己的 CRC，所以它数到 `8 + k × (X + 4)` 字节就发（`src/dxl2.c:601-643`、`src/bus.c:179-188`）。
  排在第 0 位时无需等待，**路径与 `0x82` 完全相同**——收完指令在 USART 中断里直接交给 DMA
  （`src/dxl2.c:152-171`）。microduck 的 tick 读正是这个布局。
* **错误也要保持段长**：越界读长报 `ERR = 0x10`、数据补 0；读长 > 256 或不含本机 → 静默。
  （`0x82` 是回一个*不含数据*的错误状态帧，在 `0x8A` 里那样做会让后面所有段错位。）
* `STATUS_RETURN_LEVEL = 0`、ID 列表不含本机、`LEN` 无法用 16 位表达 → **静默**。
* **`0x8A` 若指向本机（非广播）且本机不在第 0 位**：前面那些设备根本没被点名、不会发言，本机
  收不到前缀就把这次应答**作废**（`src/dxl2.c:610-624`），不会把一段属于"不存在的包"的块发到
  总线上。
* **"第一个字节还没来"与"流断在半路"不是一回事**：前导设备允许先等自己的 `return_delay_time`
  再开口（出厂值 250 ⇒ 500 µs，比本节点 500 µs 的帧内间隔阈值还长），所以本节点在**收到第一个
  字节之前**遇到空闲间隔**不作废**这次应答；一旦开始收字节再出现 > 500 µs 的间隔，就按"包已断"
  作废（`src/dxl2.c:508-528`）。两条行为都有宿主测试钉住。
* **实现注记（对固件维护者）**：本节点解析一整帧必须在**一个字节时间**（1 Mbps 下 10 µs）内
  做完，否则紧跟其后的字节会被 USART 的单字节接收寄存器覆盖丢掉——`0x8A` 的聚合帧正是"紧跟
  指令帧"发言的第一个例子。因此 CRC-16 是查表实现（`src/crc16.c:16-55`），不是按位循环。
  详见 `docs/bus_timing_borrow_plan.md §7.8`。

### 3.3 CRC-16（Dynamixel）

参数（`src/crc16.h:4-9`）：

| 参数 | 值 |
|---|---|
| 多项式 | `0x8005` |
| 初值 | `0x0000` |
| 位序 | **高位在前（MSB first，不反射）** |
| 最终异或 | 无 |
| 覆盖范围 | **整帧，含 `FF FF FD 00` 帧头，直到 CRC 字段之前** |

逐字节算法（`src/crc16.c`、`host/bus.py:160-170`）：

```
crc = 0
for byte in frame_without_crc:
    crc ^= (byte << 8)
    for _ in range(8):
        if crc & 0x8000: crc = ((crc << 1) ^ 0x8005) & 0xFFFF
        else:            crc = (crc << 1) & 0xFFFF
```

**已算好的向量**（`host/bus.py:980-982`、`host/tools/test_crc16.c`）：对 `FF FF FD 00 02 03 00 01`
（PING，ID=2）CRC = **`0x7219`**，完整帧 = `FF FF FD 00 02 03 00 01 19 72`。

### 3.4 字节填充（byte stuffing）

协议 2.0 规定：**当参数/body 中出现 `FF FF FD` 时，必须在其后再插入一个 `0xFD`**；
**`LEN` 与 CRC 都按填充后的字节计算**；接收方**只在 CRC 校验通过后**才去掉填充
（`docs/dynamixel_slave.md:41-47`）。

本节点的精确规则（`src/stuffing.c:13-45`，与官方 DynamixelSDK `addStuffing` 一致）：

1. 模式扫描**只在原始字节上进行**，插进去的 `0xFD` 不会再触发新的匹配；
2. 连续 `0xFF` 的计数在 `FF FF FF` 时**保持为 2**（"`FF FF` 后缀"在多余 `FF` 之间继续有效），
   所以 `FF FF FF FD` 也要插一个字节；
3. 匹配到"已有两个连续 `0xFF` 且当前字节是 `0xFD`"时，输出 `0xFD` 后再补一个 `0xFD`。

**已核对的向量**（`host/bus.py:999-1009`、`docs/dynamixel_slave.md:54-61`）：

| 输入 | 输出 |
|---|---|
| `01 02 FF FD 03` | `01 02 FF FD 03`（没有 `FF FF FD`） |
| `FF FF FD 07` | `FF FF FD FD 07` |
| `FF FF FD FD` | `FF FF FD FD FD` |
| `FF FF FF FD` | `FF FF FF FD FD` |

**一个真实的状态帧演练**（用 `host/bus.py` 的编解码函数计算，CRC 已核对）：

假设主机读 20 字节，参数（数据）以 `FF FF FD` 开头，body（`ERR + 参数`）为
`00 FF FF FD` + 17 个 `0x00` = 21 字节：

* 填充后 body = `00 FF FF FD FD` + 17 个 `0x00` = **22 字节**；
* `LEN = 22 + 3 = 25 = 0x19`；
* 线上帧 = `FF FF FD 00 C8 19 00 55 00 FF FF FD FD 00 …(17×00)… CRC_L CRC_H`；
* 如果**不填充**，`LEN` 就会算成 `0x18`，接收方（rustypot 会调用 `remove_stuffing`）
  会把后面的参数整体错位——这正是 §12 里"必须填充"的原因。

主机侧去填充只对**状态帧的 body**（`frame[8:-2]`）做（`host/bus.py:194-210,271`）。

### 3.5 FeeTech SCS/HLS 指令帧（主机 → 节点）

| 偏移 | 字节数 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `0xFF` | 帧头 |
| 1 | 1 | `0xFF` | 帧头 |
| 2 | 1 | `ID` | `0xFE` = 广播（`src/board.h:422`）；**禁止 `0xFD`** |
| 3 | 1 | `LEN` | 见下 |
| 4 | 1 | `INST` | 指令码（§5.2） |
| 5 | 1 | `ADDR` | 地址（只有带地址的指令才有此字节） |
| … | `n` | `DATA...` | 数据 |
| 末 | 1 | `~SUM` | 校验和 |

* **`LEN = len(params) + 2`**，其中 `params = ADDR + DATA`（无地址的指令就是只有 DATA 的
  `INST` 计数）；`LEN` 统计 **INST + ADDR + DATA + SUM**；整帧 = `LEN + 4`
  （【源码】`src/fee.c:67-68`；`飞特通讯协议说明.md §2.1`）。
  官方参考库把它写成 `LEN = 数据长度 + 3`（PING 时为 2），两者一致
  （`飞特通讯协议说明.md:58`）。
* 节点要求 `LEN >= 2`，否则丢弃并计 `bad_len`（`src/fee.c:336-341`）。
* 多字节数据**小端**（低位字节在低地址，`飞特通讯协议说明.md §6`）。

### 3.6 FeeTech 应答帧（节点 → 主机）

| 偏移 | 字节数 | 字段 | 说明 |
|---|---|---|---|
| 0..1 | 2 | `FF FF` | 帧头 |
| 2 | 1 | `ID` | 本节点 ID |
| 3 | 1 | `LEN` | **`LEN = len(DATA) + 2`**（2 = STATUS + SUM） |
| 4 | 1 | `STATUS` | **本节点恒为 `0x00`**（见 §5.4） |
| 5.. | `n` | `DATA...` | 数据（READ 的数据、SYNC_READ 的数据；其它指令为空） |
| 末 | 1 | `~SUM` | 校验和 |

【源码】`src/fee.c:37-61`。整帧 = `LEN + 4`。

### 3.7 FeeTech 校验和 `~SUM`

定义（`src/fee.c:72-90`；`飞特通讯协议说明.md §2.1-2.2`）：

```
SUM = ID + LEN + INST + ADDR + Σ DATA      # 无地址的指令：ADDR 按 0 参与求和
线上字节 = (~SUM) & 0xFF
```

* **覆盖范围**：从 `ID` 到**最后一个数据字节**（不含 `~SUM` 自身）。应答帧同理，从 `ID` 到
  最后一个数据字节（`src/fee.c:56-59`）。
* 发送无地址的指令（PING / REG_ACTION / RESET / CAL）时，`ADDR` 不在帧里出现，但**必须按 0
  参与求和**——本节点的校验循环只累加帧内真实字节，因此天然符合
  （`src/fee.c:81-83`；`飞特通讯协议说明.md:61-63`）。
* **校验错误的帧完全不应答**（SCS 协议没有"校验错应答"）；本节点计 `bad_sum` 后直接
  丢弃（`src/fee.c:84-90`）。真舵机实测同样静默（`docs/bus_timing_borrow_plan.md §1.4`）。

**已核对的向量**（`host/bus.py:1012-1014`、`飞特通讯协议说明.md §2.3`）：

| 帧 | 字节 |
|---|---|
| PING 指令（ID 200） | `FF FF C8 02 01 34`（`SUM = C8+02+01 = CB`，`~CB = 34`） |
| PING 应答 | `FF FF C8 02 00 35` |
| READ(56, 12) 指令 | `FF FF C8 04 02 38 0C ED` |

### 3.8 协议识别、100 ms 粘滞与强制锁定

**识别判据**：一帧的第 3 个字节为 **`0xFD` ⇒ Dynamixel 2.0**，否则 ⇒ **FeeTech**
（`src/bus.h:13-17`）。实现上两个解析器同时喂入：

* FeeTech 解析器在第 3 字节是 `0xFD` 时**直接拒绝并复位**（`src/fee.c:323-329`）；
* Dynamixel 解析器要求第 3 字节是 `0xFD`（`src/dxl2.c:549-556`）；
* 两者都要求前两字节是 `FF FF`（`src/dxl2.c:535-548`、`src/fee.c:308-322`）。

**100 ms 粘滞**（【设计】`BUS_PROTO_STICKY_MS = 100`，`src/bus.h:42-47`）：节点**成功应答过**
某一种协议后，该端口在 **100 ms** 内**只认这种协议**（`src/bus.c:63-92`）。目的：防止
Dynamixel 载荷里恰好的 `FF FF <本机 ID>` 被误判成 FeeTech 帧，同时让主机切换协议不必等一秒。

对一个主机实现者的**实际后果**（这一点在真机上踩过，`docs/bus_timing_borrow_plan.md §7.2`
的"主机侧测量注意"）：

> 如果先做了一次 Dynamixel 事务、紧接着（**< 100 ms**）发 FeeTech 帧，节点会把它当噪声
> **静默忽略**；现象是"命令没反应 / 设备像死了一样"。反过来也一样。

修复办法（任选其一）：

1. 同一会话里**只用一种协议**；
2. 切换协议前**等 > 100 ms**；
3. 先发一帧同协议请求把端口"粘"到目标协议上；
4. 用厂商窗 `V_PROTO_LOCK`（偏移 9；0=自动 / 1=仅 Dynamixel / 2=仅 FeeTech，`src/board.h:486`、
   `src/dev.c:247-250`、`src/bus.c:63-75`）**强制锁定**。写 `V_PROTO_LOCK=1` 或 `2` 后该端口
   对另一种协议的帧一律不解析。

一个细节：粘滞时间戳是**在节点发出应答时**更新的（`src/bus.c:88-92,103`，`bus_emit()` 是唯一
调用点）。因此**不应答的请求（例如广播写、ACK 级别 0 下的静默写）不会刷新这 100 ms 窗口**。

## 4. 时序契约（主机实现者必须遵守）

本节全部是**硬契约**：违反它不会得到"慢一点"的结果，而是丢失整条 `sync_read` 的全部数据。

### 4.1 只允许请求/应答

节点**从不主动发送**（`src/bus.c`：发送路径只有 `bus_emit()` 与 `bus_poll()`，两者都由收到
帧触发）。主机不得假设节点会周期广播，也不得在发出请求后立即改变总线方向做别的事。

### 4.2 应答槽规则（reply slot）

真舵机在 `sync_read` 中**不立即应答**：它会为 ID 列表里**每一个排在自己前面的 ID** 等一个
"应答槽"，**无论那台设备在不在线**。实测（【实测】`docs/bus_timing_borrow_plan.md §1.3`）：

| 用例（真 HD-1910，fw 3.46，1 Mbps） | 首字节 | 相对基线 |
|---|---|---|
| `SYNC_READ [1]` | 0.526 ms | 基线 |
| `SYNC_READ [7,1]`（前 1 个**缺席**） | 0.828 ms | **+0.302 ms** |
| `SYNC_READ [7,8,1]`（前 2 个缺席） | 1.121 ms | **+0.595 ms**（+0.297/个） |
| `SYNC_READ [7,8,9,1]`（前 3 个缺席） | 1.408 ms | **+0.882 ms**（+0.294/个） |

* **槽长 ≈ 295 µs**（0.294–0.302，n=21×3）。它约等于一个 21 字节应答的线上时间 210 µs +
  ≈85 µs 空隙（【实测/推算】`docs/bus_timing_borrow_plan.md §1.3`、`附录 A`）。
* **缺席设备照样占一槽**，不是"长时间超时"。所以"用总线静默 1 ms 判断缺席"是错的：k=1 时
  应答窗口 295 µs 就开了，等 1 ms 会晚一整槽并撞上后面的设备
  （`docs/bus_timing_borrow_plan.md:36,50,109`）。
* 本节点使用 **`BUS_SLOT_US = 300`**（300 µs，往上取整）作为自己的槽模型（`src/board.h:462-468`）。

### 4.3 本节点的延迟应答（k > 0 时让 k 个槽）

当 `sync_read` 的 ID 列表里本节点下标为 **k > 0** 时，节点**不立即发送**，而是先让出 **k 个槽**
再发（`src/dxl2.c:354-367`、`src/fee.c:232-242` 记录 `sync_index`；`src/bus.c:112-122` 延迟；
`src/bus_arb.c:33-44,85-98` 计时）：

* 等待期间若出现**新的、指向本机 ID 或广播的指令帧**，本次延迟应答**作废**
  （`src/bus_arb.c:46-83`；Dynamixel 的 ID 在第 5 字节，FeeTech 的 ID 在第 3 字节，靠第 3
  字节是否为 `0xFD` 区分）；
* 等待期间只收不发是合法的（半双工单线）。

**对主机的意义**：

1. 如果主机把节点排在 ID 列表**中间或末尾**，节点的应答会**晚 k × 300 µs** 到达（真机实测
   本节点延迟路径的斜率 ≈330 µs/槽，`docs/bus_timing_borrow_plan.md §7.3`：前导 ID 全缺席时
   `[200]` 基线、`[7,200]` +339 µs、`[7,8,200]` +676 µs、`[7,8,9,200]` +1001 µs）。
2. 主机**必须按 ID 匹配应答**（扫描缓冲里的 `FF FF`、用 `LEN` + 校验和确认），**不要假设
   应答按请求顺序到达**，也不要因为节点"该答却没立刻答"就判它掉线
   （`飞特通讯协议说明.md §4.1`、`host/bus.py:690-738`）。
3. 运行时（机器人控制环）**总是把 IMU 节点排在列表第 0 位**，所以热路径"收完指令立即发"
   （`src/bus.c:12-16`、`docs/dynamixel_slave.md:192`）。

> **`0x8A`（Fast Sync Read）不适用本节。** 它的应答不是各发各的状态帧，而是所有设备共拼一个
> 聚合帧（§3.2.1），每段只有约 `(X+4)×10 µs`，比 300 µs 的槽短，所以 `k > 0` 时**不能**按槽
> 让位，而是数前面 k 段的字节（`src/dxl2.c:601-643`）。`0x8A` 的 ID 列表把本节点放在第 0 位
> 仍然最省，但那是不用等，不是因为会撞包。

### 4.4 帧内字节间隙与整帧超时

* **字节间隙规则**：若**帧解析进行中**，相邻字节间隔 > **`BUS_GAP_US = 500 µs`**，则丢弃
  已收到的残帧，并在下一个 `FF FF` 上重新同步（`src/bus.h:53-56`、`src/bus.c:159-170`）。
  空闲间隔（两次事务之间）不算故障（`src/bus.c:161-163`）。
* **整帧超时**：若一帧已开始但 20 ms 内没有收完，状态机复位（`DXL_FRAME_TIMEOUT_MS = 20`，
  `src/dxl2.c:15,527-531`；`FEE_FRAME_TIMEOUT_MS = 20`，`src/fee.c:13,301-305`）。
* 因此主机**不要在一帧中间停顿超过 500 µs**；1 Mbps 下一个字节 10 µs（`docs/bus_timing_borrow_plan.md:601`）。

### 4.5 一次 16 设备组合 `sync_read` 的实测往返

真 PCBA + 15 颗真舵机，主机直接发"ID 200 + 15 颗舵机"的一次 `sync_read`（FeeTech 地址 56、
长度 15），【实测】`docs/bus_timing_borrow_plan.md §7.7`（`README.md:438`）：

| 指标 | 值 |
|---|---|
| 主机**往返**（含 USB CDC） | 中位 **8.74 ms** / p95 8.86 ms / max 8.95 ms |
| 完整性（扭矩关 / 扭矩开 / 背靠背） | 150/150 / 150/150 / 200/200 |
| 节点侧 | 每秒约 47/50 次读被应答，`echo=0 dropped=0 err=0` |

**注意区分**：8.74 ms 是**含 USB CDC 的主机往返**（【实测】）；总线上的纯串行时间由槽长
**推算**为 240 µs（指令）+ 210 µs（本节点 15 字节应答）+ 15 × 295 µs ≈ **4.9 ms**
（【估算】`docs/bus_timing_borrow_plan.md §2`）。4.9 ms 不是测量值。

主机侧还需要知道：**USB 适配器可能整块丢一次回复**（不是设备掉线）。2026-09-25 在真机 15 舵机
总线上实测到"缺失集合总是回复到达顺序的尾部，形状像一个 USB 传输块被整块丢掉"
（【实测】95 次里 60 次只收到 `200`，其余是按到达顺序连续的一段舵机 ID；同一条总线上直连的
16 ID 读 150/150 完整，数字见 `docs/bus_timing_borrow_plan.md §7.7`）。主机应**容忍/有限重试
缺失的回复**，而不是判定节点故障。

ID 过滤：只处理 `ID == 本机 ID` 或 `ID == 0xFE`（广播）。

| INST | 名称 | 方向 | 节点行为 | 出处 |

| `0x0A` | RESET | 主→从 | 恢复出厂默认 + 写 Flash；广播/quiet → 静默 | `src/fee.c:195-201` |
| `0x0B` | CAL | 主→从 | 把 2 个 0 字节写到地址 31（中位偏移 OFS），然后 ACK；广播/quiet → 静默 | `src/fee.c:203-214` |
| `0x82` | SYNC_READ | 主→从 | 参数 `ADDR(1) + nLen(1) + ID...`；命中本机 ID 才应答并按下标 k 让槽；`LEN<5` 或 `nLen=0` → 静默；不在列表 → 静默 | `src/fee.c:216-246` |
| `0x83` | SYNC_WRITE | 主→从 | 参数 `ADDR(1) + nLen(1) + (ID + DATA)×N`；命中就写；**永不应答** | `src/fee.c:248-272` |
| 其它（含 `0x09` 参数备份） | — | — | **静默忽略**（既不执行也不应答） | `src/fee.c:274-277` |

**"quiet" 的定义**（ACK 应答级别，寄存器 8，`src/fee.c:22-27,97-100`）：寄存器 8 = 0 时，
除 **PING / READ / SYNC_READ** 之外的指令**照样执行，只是不应答**；= 1（默认，
`src/dev.c:198`）时全部应答。写寄存器 8 本身立即生效（它是镜像里的字节，`ack_level()` 每次
现读）。

### 5.4 FeeTech 应答 STATUS 字节：恒 0，且**不是**舵机故障字

本节点的 FeeTech ACK `STATUS` 字节**永远是 `0x00`**（`FEE_ST_OK`，`src/fee.c:20,29-35`）。

原因（源码注释，`src/fee.c:15-19`）：真舵机的 STATUS 是**舵机**状态字（过压、编码器、温度、
电流、负载），**飞特工具会把非 0 的 ack 状态当成舵机故障**；本项目自己的主机补丁也曾把
`status != 0` 当整条事务失败。所以：

* 本节点**绝不**在这里报告自己的协议错误；
* 最近一次被拒绝/夹紧的协议错误放在**厂商窗 `V_LAST_ERR`**（DXL 167 / Fee 179，偏移 19，
  `src/board.h:496-500`、`src/dev.c:139`、`src/dev.c:717-723`），主机需要时**主动去读**；
* READ 出错时节点回一个**数据长度为 0 的 ACK**（`src/fee.c:121-123`），主机应把
  "应答数据长度 < 请求长度"当成失败信号，再去问 `V_LAST_ERR`。

`V_LAST_ERR` 里存的是 `DXL_ERR_*`（§5.3）的值。它**会被后续错误覆盖，固件不主动清零**。

### 6.3 为什么要有 15 字节契约块（以及主机在混合车队里的规则）

真 HD-1910 在地址 56 起的**文档化块就是 15 字节**：位置/速度/负载/电压/温度/状态/移动/电流；
再往后（71..76）是别的寄存器，不是为外部设备预留的（【实测】`docs/bus_timing_borrow_plan.md §1.2`、
`飞特通讯协议说明.md §13.3`）。

而运行时对**节点和 15 颗舵机用的是同一个 `sync_read`**（地址 56、长度 15），所以：

> **主机在混合车队里必须读 15 字节（地址 56）**，这样一次事务同时拿到节点遥测和全部舵机状态。
> 读 20 字节虽然本机 fw 3.46 的舵机也答应，但每个应答多 5 字节 ⇒ 每台约 +50 µs ⇒ 事务从
> ≈4.9 ms 涨到 ≈5.7 ms，逼近 6 ms 验收线；而且"读超出文档块长"在别的型号/固件上不保证
> （【实测+估算】`docs/bus_timing_borrow_plan.md:46-49,188`）。

因为计数和状态必须塞进这 15 字节，**原始加速度放不下**，所以它只存在于 128 别名的 20 字节
诊断块里（`src/board.h:453-456`、`docs/bus_timing_borrow_plan.md §0 D1`）。

### 6.5 四元数字节全 0 = 融合尚未收敛（主机必须保持上一有效值）

**规则：当 `TELEM_FLAG_SFLP_VALID`（bit0）为 0、且四元数 6 个字节全为 0 时，表示融合还没有
收敛；主机必须沿用自己上一份有效姿态，不能把全 0 当成"单位四元数/静止"。**

* 真驱动：芯片的数据手册给出 SFLP 校准 0.8 s + 姿态稳定 0.7 s ≈ **1.5 s**，固件用
  `LSM_SFLP_CONVERGE_MS = 1500` 主动保持这个窗口：期间**发布零四元数字节**并清 `SFLP_VALID`，
  但 `FUSION_OK` 仍为 1（算法在跑），窗口结束后 flush FIFO 再恢复发布
  （`src/lsm6dsv16x.h:137-145`、`src/imu_spi.c:219-239,603-616`）。
* 【实测】重启后的实际窗口（`docs/bus_timing_borrow_plan.md §7.6`、`README.md:436`）：
  写 `VCMD_RESET_SIM` 后 **9–13 ms** 四元数字节归零；**1.51–1.52 s** 后恢复非零（< 2.5 s）。
* 模拟器：`SIM_MODE=5 sflp-wait` 制造同样的"陀螺正常、四元数全 0"状态，用于验证主机的
  "保持上一有效值"逻辑（`src/imu_sim.h:24`、`README.md:219`）。
* 主机侧参考实现就是这么做的：`host/bus.py:535-541` 只在 `quat_valid` 时更新 `last_quat`。

> 主机不要用全 0 四元数去重建 `w=1`：那样会把"没有姿态"误判成"姿态为单位四元数"，
> 得到一串假的零角速度姿态。`FUSION_OK` 与 `SFLP_VALID` 的组合才是判据
> （`src/imu_spi.c:603-607`）。

### 7.3 锁标志（FeeTech 寄存器 55）的精确语义

【源码】`src/dev.c:754-760`：当 `55 != 0` 且写入地址 `< 40` 时，写入**仍然进入 RAM 镜像并
立即生效**，只是**不标记为需要持久化**（掉电后回到 EEPROM/默认值）。它的手册语义是
"EPROM 写入是否掉电保存"，**不是"是否允许写"**（`飞特通讯协议说明.md §10.3.1, §5.3`）。

本节点的默认值是 **0（可持久化）**，与手册初始值 1 不同，是**有意的偏差**，这样主机改 ID/
波特率后能直接存下来（`src/dev.c:203-207`）。

### 7.4 两种映射的对应关系，以及"写只读区"的差异

| 语义 | Dynamixel 地址 | FeeTech 地址 |
|---|---|---|
| 型号 / 固件版本 | 0..1 / 6 | 3..4 / 0..1 |
| ID / 波特率 | 7 / 8 | 5 / 6 |
| 遥测（20 字节诊断块） | 124..143 | 128..147（别名） |
| 遥测（15 字节契约块） | —（DXL 无 15 字节形态） | 56..70 |
| 厂商配置窗 | 148..167 | 160..179 |
| 身份窗 | 180..195 | 180..195（同址） |
| 升级会话窗 | 208..255 | 208..255（同址） |

**写只读区的差异（主机必须知道）**【源码】`src/dev.c:762-792`：

* **Dynamixel：整帧拒绝**。写操作只要有一个字节落在只读范围，**整个写被拒绝**并返回
  `ERR=0x02`（ACCESS）。所以 DXL 下写身份窗/升级窗会得到明确的 ACCESS 错误——这正是
  节点提示主机"先进入 boot 模式"的方式（`src/dev.c:618-621`）。
* **FeeTech：接受但忽略**。只读字节被跳过检查、其余字节仍写入镜像；随后主循环发布时会把
  只读字段（遥测、身份窗等）用真实值覆盖。**因此 FeeTech 下写身份窗或升级窗不会报错，
  而是"静默无效"**——一个主机错误地以为"写 208 就已经开始升级"时会毫无提示。
  （`src/dev.c:772` 的 `continue`。）

### 8.2 读写规则（重要）

* **可写字段**：偏移 0..17（含 magic）可写；`STATUS`(18) 与 `LAST_ERR`(19) 可写但被忽略，
  节点每次发布都用真实状态覆盖（`src/dev.c:135-141,635-638`）。为什么不让它们只读：主机
  习惯**一次写整 20 字节窗口**，如果拒绝会让可用字段一起写不进去（`src/dev.c:635-638`、
  `docs/dynamixel_slave.md:146-148`）。
* **命令执行需要 magic**：`vendor_apply()` 先读窗口 magic，不等于 `0x4D49` 就直接
  return（`src/dev.c:221-223`）。实践中窗口里本来就存着 magic，所以**单独写偏移 2 一个字节
  也能执行命令**；但稳妥的做法是**读回整窗 → 改字段 → 整窗写回**（`host/upgrade.py:457-460,428-431`
  的 `ask_for_boot()` / `confirm_image()` 就是这么做的）。
* **命令执行时机**：写入落在窗口内（`addr+len` 与 `[base, base+19]` 相交）时，
  `dev_write()` 末尾调用 `vendor_apply()`（`src/dev.c:782-790`）。命令被消费后节点把 `CMD`
  清 0，所以**读窗口永远读到 `CMD=0`**（`src/dev.c:268-270`、`src/dev.c:140`）。
* **写窗口不会被"整帧拒绝"波及**：Dynamixel 的 `ro_dxl()` 特意**不**把 148..167 视为只读
  （`src/dev.c:635-638`），所以 20 字节整窗写入不会被 ACCESS 拒绝。

## 10. 升级协议

本节是本文重点。升级**不引入任何新帧类型**：Dynamixel 用 `INST_READ/WRITE`、FeeTech 用
`READ/WRITE`，都是普通寄存器读写（`docs/upgrade.md:196-199`、`src/boot_upgrade.h:5-9`）。

> **升级走哪条线，取决于主机把帧发到哪条线。** 升级窗（208..255）就是普通寄存器，
> 协议层不区分端口：节点在 USART1（电机总线）上服务它；台架实验构建
> （`BUS_MIRROR_ENABLE=1`）里 USART0 也服务它。默认构建里 USART0 是**只输出 DBG_ 日志的
> 调试口**，根本不解析帧（`BUS_MIRROR_ENABLE = 0`），所以对调试口发协议只会超时。
> 端口的正确性由主机工具负责：`host/upgrade.py` 的 `--port` 默认 `auto`，**逐个探测**
> `ttyACM0-1`、`ttyUSB0-5`、`ttyS2` 里存在的设备，取第一个真能应答节点的那个并打印结果
> （存在的 `ttyUSB*` 不按名字排除，按应答判断），同时拒绝和另一个主机抢端口（机器人上是
> robotd）。

### 10.1 如何通过总线进入 / 离开 bootloader

**进入（应用态 → bootloader）**：

1. 主机向厂商窗（DXL 148 / Fee 160）写 `V_CMD = 6`（`VCMD_BOOT`），通常做"读回整窗 →
   改 magic(0..1) 和 cmd(2) → 整窗写回"（`host/upgrade.py:451-478`）。
2. 节点：置持久化 `boot_stay = 1` → 立即写配置页 → 写 SRAM 握手字 → 安排 **50 ms** 后软复位
   （`src/dev.c:501-510`、`src/dev.c:836-840`）。应答先发出去。
3. 复位后 bootloader 看到 `boot_stay`（或 SRAM 握手字）就**停在 boot 模式**服务总线
   （`src/boot_main.c:370-377,388-411`）。主机轮询身份窗，`UID_MODE` 变成 1 即已进入
   （`host/upgrade.py:464-478`，默认 6 s 超时）。
4. **如何识别"在 bootloader"**（任一即可）：
   * 身份窗 `UID_MODE = 1`（最可靠）；
   * Dynamixel `PING` 返回型号 `0xB007`（`BOOT_MODEL_NUMBER`，`src/board.h:160`）；
   * FeeTech `READ 3..4` 返回 `0x00B7`（`BOOT_FEE_MODEL_NUMBER`，`src/board.h:161`）；
   * Dynamixel 固件版本寄存器 6 = 0（`src/boot_regs.c:98`）。

**离开（bootloader → 应用）**，三种方式：

1. `UPG_CMD_REBOOT`（命令 6）：bootloader 清 `boot_stay` 并写配置页，50 ms 后复位，按启动
   决策运行（通常是刚提交的 trial 镜像）（`src/boot_upgrade.c:396-402`、`src/boot_regs.c:54-60`）。
2. **主机消失超时**：只要有一个可启动槽，boot 模式在 **`BOOT_IDLE_EXIT_MS = 30000`**（30 s）
   没有收到任何总线帧后，清 `boot_stay` 并正常启动（`src/board.h:177`、`src/boot_main.c:324-329`）。
   这是"主机失联不会把机器人吊死"的兜底。
3. 断电重启：`boot_stay` 是**持久化**的，所以单纯断电会再次进 boot 模式；30 s 无主机后仍会
   自动退出（同上）。收尾时应显式发 `UPG_CMD_REBOOT`，或等 idle 超时。

> `VCMD_BOOT` 依赖配置页可写和 SRAM 握手字跨软复位（SRAM 无 VBAT，不跨掉电，
> `src/boot_ram.h:16-19`）；持久化的 `boot_stay` 才是跨掉电的那一半（`src/board.h:163-168`）。

### 10.2 升级会话窗（208..255，48 字节，两种协议同址）

窗口基址 `UPGRADE_WIN_ADDR = 208`、长 48；数据窗 `UPGRADE_DATA_ADDR = 240`、长 16

### 10.5 主机操作步骤（逐条）

以下顺序即 `host/upgrade.py` 参考实现（`Upgrader`，`host/upgrade.py:514-736`）。
**关键：块写长度由"实际写入数据窗的字节数"决定**，不是由主机声明的 `U_BLKLEN` 决定
（`src/boot_upgrade.c:456-465`；`docs/upgrade.md:242-247`）。

#### 步骤 0：确认在 bootloader、选定目标槽

读身份窗（§9）；要求 `UID_MODE = 1`。若目标是节点当前运行的槽，拒绝并改刷另一个槽
（`host/upgrade.py:884-895`）。`.ipkg` 里 `slot != 255` 时目标槽由包决定（`host/upgrade.py:774-782`）。

#### 步骤 1：打开会话（写 magic + 参数）

```
write(U_MAGIC_L, 0x4247 LE)     # 208..209
write(U_TARGET, target)         # 212
write(U_IMGLEN_0, image_size)   # 232..235
write(U_IMGCRC_0, host_crc)     # 236..239（两段拼接 CRC-32）
write(U_VER_L, image_version)   # 225..226
```
（`host/upgrade.py:565-575`。）

#### 步骤 2：`UPG_BEGIN`

```
write(U_CMD, 1)
read  U_STATUS(211) 起 24 字节   # 一次读拿到 status/errcode/ack_seq/node_crc（偏移 3..22）
```
期望 `U_STATUS == 1 (ERASED)`。擦除时间取决于页数：**≈25 ms/页**（【实测/估算】
`docs/bus_timing_borrow_plan.md:616`），所以超时给 ≥2 s（`host/upgrade.py:576-589` 用 4 s）。
擦除期间节点**不响应总线**，主机必须暂停对舵机的轮询（`docs/flash_layout.md:538-541`）。

#### 步骤 3：`DATA` 块循环

每块 16 字节（最后一块由包的长度决定；`.ipkg` 打包时已把镜像补齐到 4 的倍数，
`host/package.py:480-488`，所以每块都是 4 的倍数）。参考实现把"控制字段 + 数据"放在**一帧**里
（从窗口偏移 5 = 地址 213 开始，到数据结束），并在帧内把经过的 `ver/imglen/imgcrc` 重新填一遍，
避免被这一帧覆盖成 0（`host/upgrade.py:514-522,532-544`）：

```
frame = seq(2) | off(4) | blklen(1) | blkcrc(2) | (ACK_SEQ+ERRCODE 222..224 只读，填空) |
        ver(2) | (NODE_CRC+RESERVED 227..231 只读，填空) | imglen(4) | imgcrc(4) | data(n)
write(213, frame)                # 一次写：命令由数据窗触发
read  U_STATUS(211) 起 24 字节   # 校验 status/ack_seq
```

**块的规则**：

* **偏移**必须 **4 字节对齐**（`src/boot_upgrade.c:216`）；
* **长度** = 实际写入数据窗的字节数 `n`，必须 **4..16 且是 4 的倍数**（`src/boot_upgrade.c:459-478`）；
* **每块 CRC-16** = `crc16_dxl(data[0..n-1])`（§3.3），节点独立复算并比对；
* **序号**：`seq == ack_seq + 1` 为新块（接受并前移 `ack_seq`）；`seq == ack_seq` 为**重传**
  （幂等：同一偏移重写同样内容，`bytes_written` 不重复计）；其它值 → `RANGE`(2)，**不碰 Flash**，
  主机应从 `U_ACK_SEQ` 重新同步（`src/boot_upgrade.c:226-236,250-256`）；
* 节点写完后**立即回读比对**，不一致算 `FLASH`(3)（`src/boot_upgrade.c:242-248`）；
* 参考实现每块失败最多重试 3 次，**重发同一个 `seq`**（`host/upgrade.py:605-635`）。

也可以拆成两帧（控制帧写 213 的 9 字节，再单独写数据窗 240）：`UPG_CMD_DATA` 只把状态置为
`RECEIVING`，随后的数据窗写入触发块编程。C 测试两种写法都覆盖（`docs/flash_layout.md:796`）。

#### 步骤 4：`UPG_END`

```
write(U_CMD, 3)
read  U_STATUS(211) 起 24 字节
```
节点重算 `crc32(low || high)` 并与 `U_IMGCRC` 比对，再回读应用头校验
（magic / header_version / `image_size` / 两段 CRC / entry / board_id / proto_version / no-boot），
全部通过才提交。期望 `U_STATUS == 5 (COMMITTED)`，并可在 227..230 读到节点 CRC 与主机值比对
（`src/boot_upgrade.c:262-319`；`host/upgrade.py:637-653`）。

#### 步骤 5：`READBACK`（可选，验证落盘）

```
write(U_MAGIC_L, 0x4247)   # arm（不擦任何东西）
write(U_TARGET, target)
对每个 chunk：
    write(U_OFF_0, offset + n + blklen(chunk))   # 写 5 字节：off(4) + blklen(1)
    write(U_CMD, 7)
    read  (U_DATA_OFF = 240, chunk)
```
**每个 chunk 都必须重新发一次 `READBACK`**：数据窗只在命令执行时刷新，重复读同一窗口只会
拿到第一段（`host/upgrade.py:667-693` 的注释）。`U_BLKLEN` 在 readback 里允许 **1..16**
（不像块写必须 4 的倍数，`src/boot_upgrade.c:356`）。

#### 步骤 6：`CONFIRM`

* 若节点已重启进应用：向厂商窗写 `V_CMD = 5`（`VCMD_CONFIRM`）立即确认（`host/upgrade.py:481-492`）。
* `UPG_CMD_CONFIRM`（升级窗命令 5）在 boot 模式**总是报 `STATE`**，不要用它（§10.3）。
* 不显式确认也可以：应用跑够 30 s（期间至少答过一次总线帧）会自己确认（§10.6）。

#### 步骤 7：`REBOOT`

```
write(U_CMD, 6)
```
bootloader 清 `boot_stay`、复位；主机轮询身份窗直到 `UID_MODE` 变回 0（应用）
（`host/upgrade.py:661-665,878-892`）。

**幂等性小结**：`seq == ack_seq` 的重传是幂等的（重复编程同一偏移、同样内容）；
`READBACK` 是可重复的只读操作；`ABORT` 不改已写 Flash；`BEGIN` **不幂等**（它会擦除并重置
`ACK_SEQ`）。`U_CMD` 读回恒 0。

### 10.6 trial / 确认 / 回滚语义

| 事件 | 结果 | 出处 |
|---|---|---|
| `UPG_END` 提交成功 | 配置页：`trial_slot = 目标槽`、`attempts = 0`、`pingpong +1`、`boot_stay = 0` | `src/boot_regs.c:42-52` |
| 复位且存在有效 trial 槽、`attempts < 3` | 运行该槽，`attempts + 1`，**且在跳转前持久化** | `src/boot_decide.c:41-47`；`src/boot_main.c:389-401` |
| 应用连续运行 ≥ **30 s**（`BOOT_CONFIRM_MS`）且期间答过至少一次总线帧 | 自我确认：`boot_slot = 自己`、`trial_slot = 无`、`attempts = 0`、`pingpong +1`，写配置页 | `src/board.h:175`；`src/dev.c:479-499,460-477` |
| 应用运行 ≥ **60 s**（`BOOT_CONFIRM_LONE_MS`）但从未收到主机帧 | 同样确认（否则一台没人理的机器人会永远回滚） | `src/board.h:176`；`src/dev.c:491-496` |
| `attempts` 达到 **3** 仍未确认 | **放弃 trial、回滚**到上一个已确认槽，`attempts` 清零 | `src/board.h:174`；`src/boot_decide.c:48-57` |
| 主机显式确认 | 厂商窗 `V_CMD = 5` | `src/dev.c:286-288` |
| 主机显式切槽 | 厂商窗 `V_CMD = 7`，下次复位跑另一个槽 | `src/dev.c:512-525` |
| 配置页写失败且 `attempts+1 >= 3` | 在 RAM 中**强制改用回滚决策**，不等下次写入成功 | `src/boot_main.c:393-401` |

**为什么这套设计不会变砖 / 不会擦掉最后一个可启动镜像**（三条独立保证）：

1. **物理上只能写槽**：升级状态机只通过 `boot_flash_slot_erase/program` 写 Flash，而它们
   只接受 slot A/B 的偏移；越界、未对齐、slot 非法一律拒绝
   （`src/boot_flash.c:33-59,218-262`；`src/boot_upgrade.h:12-16`）。bootloader 区与配置页在
   升级路径里**不可达**。
2. **绝不擦最后一个可启动镜像**：`BEGIN` 拒绝"目标槽 == bootloader 将要运行的槽、且另一个槽
   不可启动"的组合（`src/boot_upgrade.c:159-164`；`src/boot_main.c:176-181` 提供
   `other_bootable`）。主机侧也会主动避开正在运行的槽（`host/upgrade.py:884-918`）。
3. **失败有退路**：应用头由打包工具写好、节点只回读校验（节点**不重写**头，见 §10.7）；
   每块都有独立 CRC-16 与写后回读；整镜像有两段 CRC-32；trial 计数在跳转前持久化，写失败也
   在 RAM 里强制回滚；两个槽都不可启动时 bootloader **无限期**停在 boot 模式等主机刷机
   （`src/boot_main.c:274,324-329`——`any_bootable == 0` 时不设 idle 超时）。

| 28 | 2 | `board_id` | `APP_BOARD_ID = 1` |
| 30 | 2 | `proto_version` | `APP_PROTO_VERSION = 1`（总线升级协议版本） |
| 32 | 2 | `flags` | `APP_HDR_FLAG_TRIAL(0x0001)` / `CONFIRMED(0x0002)` / `NO_BOOT(0x0004)` |
| 34 | 30 | `reserved` | 0 |

**三个 CRC 的关系**（`src/app_header.h:74-85`、`host/package.py:130-145`）：

* `crc_low` / `crc_high` 是 bootloader 每次启动都要算的"两段独立校验"（头自身不参与，避免自指）；
* `payload_crc32 = zlib.crc32(high, zlib.crc32(low))`，即两段**按顺序拼接**后的一个 CRC-32；
  它同时是 `.ipkg` 的 `payload_crc32` 和升级时写入 `U_IMGCRC` 的值（`host/upgrade.py:701`）；
* `full_crc32` 只用于包文件完整性（防下载截断），节点不校验它。

**节点在 `UPG_END` 验证的东西**（`src/boot_upgrade.c:262-305`）：
整镜像 CRC-32 == `U_IMGCRC`；`app_header_check()` 全过；`h.image_size == U_IMGLEN`；
`U_VER != 0` 时 `h.image_version == U_VER`；entry 落在目标槽内。

**节点不重写应用头**（`src/boot_upgrade.c:280-288`；`docs/upgrade.md:256-257`）：头由打包工具
写好（头不参与两段 CRC），节点只回读校验。原因：Flash 只能把 1 写成 0，节点重写可能写不进
"更新"的位（例如把 `CONFIRMED` 改回 `TRIAL` 需要把 0 置 1）。

## 11. 最小可用示例（可拷贝的字节序列）

以下所有帧都是**用 `host/bus.py` 的编解码函数计算**的（`dxl_read` / `fee_read` /
`dxl_sync_read` / `fee_sync_read` / `dxl_write` / `fee_write`），并用同一模块的
`dxl_parse_status` / `fee_parse_ack` 反向校验过；CRC/校验和都是算出来的，不是抄的。
节点 ID 取默认 **200 = `0xC8`**。

### (a) FeeTech 读 15 字节契约块（地址 56）

请求（`fee_read(200, 56, 15)`）：

```
FF FF C8 04 02 38 0F EA
```

逐字节：`FF FF` 帧头；`C8` = ID 200；`04` = LEN = `len(params)+2` = `2+2`；`02` = READ；
`38` = 地址 56；`0F` = 长度 15；校验和：
`SUM = C8 + 04 + 02 + 38 + 0F = 0x115 → 0x15`，`~0x15 = 0xEA`。

应答形状：`FF FF C8 11 00 <15 字节数据> ~SUM`（LEN = `15+2` = `0x11`，整帧 21 字节）。
一个**示例**数据 `00 01 … 0E` 的应答（用 `fee_parse_ack` 校验通过）：

```
FF FF C8 11 00 00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E BD
```

校验和：`SUM = C8+11+00+(00+…+0E=0x69) = 0x142 → 0x42`，`~0x42 = 0xBD`。
解码时第 13 字节（地址 68）= 采样计数、第 14 字节（69）= 状态位、第 15 字节（70）恒 0（§6.2）。

### (b) Dynamixel 读 20 字节遥测窗（地址 124）

请求（`dxl_read(200, 124, 20)`）：

```
FF FF FD 00 C8 07 00 02 7C 00 14 00 AB 87
```

`07 00` = LEN = 参数(2+2) + 3 = 7；`02` = READ；`7C 00` = 124 LE；`14 00` = 20 LE；
CRC-16 = **`0x87AB`**（低字节在前：`AB 87`）。

应答形状：`FF FF FD 00 C8 18 00 55 00 <20 字节> CRC_L CRC_H`（LEN = 24 = `0x18`）。
一个**示例**数据 `00 … 13` 的应答（`dxl_parse_status` 校验通过）：

```
FF FF FD 00 C8 18 00 55 00 00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F 10 11 12 13 70 4C
```

（`docs/bus_timing_borrow_plan.md:602-603` 给出另一个已核对向量：16 ID 指令帧 240 µs、
单应答帧（15 字节块）210 µs。）

### (c) Dynamixel `sync_read` 覆盖节点 + 舵机

节点必须排在 ID 列表**第 0 位**：它在第 k 位就会把应答延后 k 个槽（见 §4），排错会让自己
的应答与前面设备的应答撞车。若主机走 Dynamixel 协议读 12 字节控制块，以本机真机的 ID 为例：

```
dxl_sync_read([200, 10, 20], 124, 12)
= FF FF FD 00 FE 0A 00 82 7C 00 0C 00 C8 0A 14 AF 27
```

`FE` = 广播 ID；`0A 00` = LEN = 参数(2+2+3) + 3 = 10；`82` = SYNC_READ；
`7C 00` = 地址 124；`0C 00` = 长度 12；`C8 0A 14` = ID 列表 `[200,10,20]`；CRC = `0x27AF`。

（本机真机实际走的是下面那条 FeeTech 布局；这条是给 Dynamixel 主机的等价写法。）

**FeeTech 混合车队的实际布局**（节点 + 15 颗真舵机，地址 56、长度 15）：

```
fee_sync_read([200,10,11,12,13,14,20,21,22,23,24,30,31,32,33,34], 56, 15)
= FF FF FE 14 82 38 0F C8 0A 0B 0C 0D 0E 14 15 16 17 18 1E 1F 20 21 22 12
```

`14` = LEN = `(2 + 16) + 2`；`82` = SYNC_READ；`38` = 56；`0F` = 15；随后 16 个 ID
（`0A`=10 … `22`=34）；校验和 `12`。主机要按 ID 收齐 16 帧应答（§4.3）。

### (c2) Dynamixel `fast_sync_read`（`0x8A`）覆盖节点 + 舵机

指令与 `sync_read` 同形，只把 `82` 换成 `8A`；**应答是一个 `ID=0xFE` 的聚合帧**（§3.2.1）。
microduck 的 tick 读（`[200] + 15 关节`，地址 124、长度 12）在总线上是：

```
fast_sync_read([200,20,21,22,23,24,30,31,32,33,34,10,11,12,13,14], 124, 12)
= FF FF FD 00 FE 17 00 8A 7C 00 0C 00 C8 14 15 16 17 18 1E 1F 20 21 22 0A 0B 0C 0D 0E 5F 95
```

`17 00` = LEN = 参数(4 + 16) + 3 = 23；`8A` = FAST_SYNC_READ；`7C 00` = 地址 124；`0C 00` = 长度
12；随后 16 个 ID；CRC = `0x955F`。**这串字节与 rustypot 1.8 自己生成的逐字节相同**
（`host/tools/rustypot_check` 断言 rustypot 写出的就是它，`host/tools/test_protocols.c` 也把同一
常量钉在固件测试里）。

本节点排在**第 0 位**时的应答只有 24 字节——8 字节前缀 + 自己那一段：

```
= FF FF FD 00 FE 01 01 55 00 C8 <12 字节遥测> CRC_L CRC_H
```

* `FE` = 聚合帧 ID；`01 01` = LEN = **1 + 16 × 16 = 257**（整包 264 字节，覆盖全部 16 台）——
  本节点发的是**整包长度**，不是自己那 24 字节；
* `55` = 状态标记；`00` = 本段 `ERR`；`C8` = 本段 `ID`（200，不是 `FE`）；
* 末 2 字节是**累积 CRC**，覆盖前缀 + 本段。用固定寄存器镜像（偏移 124..135 = `00 01 … 0B`）
  复现时是 `8E A1`——`host/tools/test_protocols.c` 逐字节钉住这 24 字节，
  `host/tools/rustypot_check/src/main.rs` 把**同一个常量**喂给真 rustypot。

后面 15 台的段由舵机各自追加（每段 `ERR ID DATA(12) CRC(2)`，共 16 字节；每段 CRC 覆盖到本段
为止）。主机侧解码用 `host/bus.py`：

```python
import bus
frame  = ...                       # 总线上的 264 字节聚合帧
ids    = [200,20,21,22,23,24,30,31,32,33,34,10,11,12,13,14]
values = bus.dxl_parse_fast_sync_read(frame, ids, 12)
# -> [(data12, err), ...] 共 16 项，顺序与 ID 列表一致；任何一段 CRC 或 ID 不符都抛 ProtocolError
```

真机自检（三种位置都跑）：

```
host/tools/py.sh host/tools/fast_sync_read_check.py --port /dev/ttyACM0
host/tools/py.sh host/tools/fast_sync_read_check.py --self-test     # 不需要硬件
```

**2026-09-30 真机结果【实测】**（GD32 节点挂在 `/dev/ttyACM0`，与 15 颗 FeeTech 舵机同线，
`BUS_MIRROR_ENABLE=0` 镜像，走 A/B 升级刷入、未擦片）：**19/19 通过**——第 0 位的 24 字节应答
（`FE`/`LEN = 257`/`ERR = 0`/`ID = 200`/累积 CRC）补上 15 段合成舵机段后 264 字节整包被参考解析器
逐段接受且第 0 段就是本节点遥测；第 1 位收满前缀+前导块后立刻发出自己那 16 字节块；未被点名与
"只发块不发前缀"两种情况下静默；`0x8A` 与 `0x82` 在采样计数未变时返回**完全相同的字节**；
20 次背靠背 0 丢失。**真 XL330 同总线的完整 16 设备读仍未验证**（§15.5 第 11 项）。

### (d) 进入 bootloader

先读回厂商窗（DXL `dxl_read(200,148,20)` = `FF FF FD 00 C8 07 00 02 94 00 14 00 86 27`），

（magic `0x4D49`；CMD=6 = `VCMD_BOOT`；SIM_MODE=0；SIM_AMP=1000=`E8 03`；
SIM_FREQ=1000=`E8 03`；REPORT_FRAME=0；PROTO_LOCK=0；三个 bias=0；MIRROR_BAUD=0；
DBG_LEVEL=2；STATUS=0；LAST_ERR=0）。

**Dynamixel**（`dxl_write(200, 148, window)`）：

## 12. 实现者易踩的坑

1. **100 ms 协议粘滞会伪装成"命令没做任何事"。**
   症状：先做了一次 Dynamixel 事务，< 100 ms 后发 FeeTech 帧（或反之），节点**完全没反应**，
   也不报错，像设备死机。修复：同一会话只用一种协议 / 切换前等 > 100 ms / 先发一帧同协议
   请求 / 写 `V_PROTO_LOCK` 强制锁定。（`src/bus.c:63-92`；真机案例见
   `docs/bus_timing_borrow_plan.md §7.2` 的"主机侧测量注意"。）

2. **混合车队里 FeeTech 必须读 15 字节。**
   症状：对 IMU 节点和舵机用同一个 `sync_read(56, 20)`，节点能答但舵机的"文档化块"只有
   15 字节，事务时间从 ≈4.9 ms 涨到 ≈5.7 ms，逼近 6 ms 验收线；换型号/固件还可能直接失败。
   修复：统一按 **地址 56、长度 15** 读（§6.3）。

3. **四元数全 0 = 融合没收敛，不是"单位四元数"。**
   症状：主机把 6 个 0 字节解码成 `w = √(1-0) = 1`，于是姿态突然跳回单位四元数、角速度
   出现假值；重启融合后持续约 1.5 s。修复：`SFLP_VALID`(bit0) 为 0 时**保持上一有效姿态**
   （§6.5）；实测归零 9–13 ms、1.51–1.52 s 恢复。

4. **节点排在 `sync_read` 列表第 k 位时会晚 k 个槽应答。**
   症状：主机只等到"第一个应答"就结束突发，节点（在列表中部/末尾）的应答被整段丢掉；
   或误判"节点掉线"。修复：按 ID 收集应答、给足超时（k × 300 µs）；运行时把节点排在第 0 位
   （§4.3）。

5. **Dynamixel 状态帧必须做字节填充；主机必须先去填充再解参数。**
   症状：参数里出现 `FF FF FD` 时帧长度/字段全部错位（rustypot 会调用 `remove_stuffing`）。
   修复：按 §3.4 的规则生成/解析；**只在 CRC 校验通过后**去填充（`src/dxl2.c:22-24,205-212`、
   `host/bus.py:269-274`）。

6. **FeeTech 的 ACK `STATUS` 恒 0，不等于"命令一定成功"。**
   症状：READ 越界时节点回 `STATUS=0` 但**数据长度为 0**；主机若只看 STATUS 会以为读到空值。
   修复：校验应答数据长度 == 请求长度，失败时读厂商窗 `V_LAST_ERR`（DXL 167 / Fee 179）
   （§5.4）。

7. **写可以被拒绝，原因在厂商窗 `V_LAST_ERR`。**
   Dynamixel：被拒的写返回 `ERR=0x02`（ACCESS）或 `0x10`（RANGE），同时记入 `V_LAST_ERR`；
   FeeTech：ACK 永远是 STATUS 0，**只能**从 `V_LAST_ERR` 查原因；应用态对身份窗/升级窗的写
   在 DXL 下是 ACCESS、在 FeeTech 下是**静默无效**（§7.4）。另外 `V_LAST_ERR` 只被
   "后续错误"覆盖，固件不清零。

8. **USB 串口适配器可能整块丢一次回复，不要据此判定设备故障。**
   症状：`sync_read` 的应答集合总是"尾部缺一段"（实测 95 次里 60 次只有 `200`，其余是
   按到达顺序连续的一段舵机 ID），形状像"一个 USB 传输块被整块丢掉"；直连总线的同样
   16 ID 读取 150/150 完整。修复：主机容忍/有限重试缺失的回复；`robotd` 的"沿用上一份好
   样本 + consecutive_errors"就是安全兜底。（【实测】2026-09-25 真机 15 舵机联调，
   `docs/bus_timing_borrow_plan.md §7.7` 与 §4.6 记录的是同一次测量与同类主机侧截断。）

9. **`0x8A` 的应答不是"每台一个状态帧"，而是一个聚合帧。**
   症状：主机按普通状态帧逐帧解析，只看到第 0 台的 8 字节前缀与第一段，剩下的段被当成噪声；
   或者期待字节填充（聚合帧**不填充**），数据里出现 `FF FF FD` 时字段错位。修复：按 §3.2.1
   处理——`LEN = 1 + N×(X+4)` 覆盖整包、每段 `ERR + ID + DATA + 累积 CRC`、按 ID 列表顺序取数；
   `host/bus.py` 的 `dxl_parse_fast_sync_read()` 就是参考实现。另注意它**全有或全无**：任何一台
   被点名的设备不应答（或不应答 `0x8A`）都会让整包作废，所以老固件/旧舵机上必须留着
   `bus.fast_sync_read = false` 这个开关。

10. **帧中间不要停顿 > 500 µs，两帧之间可以。**
   症状：主机分片写一帧或调试打印卡在中间，节点把残帧丢掉并重新同步，表现为"偶发坏帧"。
   修复：一帧一次性写出（§4.4）。

10. **`UPG_BLKLEN` 不是 1..16，而是 4/8/12/16。**
    症状：主机写 5 字节块被拒（`UPG_ERR_LENGTH=8`），或块长与 `U_BLKLEN` 不一致被拒。
    修复：块长取 4 的倍数、≤16；最后一块也要靠打包工具把镜像补到 4 的倍数（§10.5）。

11. **`UPG_CMD_CONFIRM` 在 bootloader 里一定报 `STATE`。**
    症状：主机以为可以像别的 bootloader 一样用升级窗命令 5 确认新镜像，得到
    `STATUS=0x84`。修复：确认走厂商窗 `V_CMD=5`，或在应用启动后再确认（§10.3、§10.6）。

12. **擦除期间节点不响应总线。**
    `UPG_BEGIN` 按页擦除，**≈25 ms/页**（实测/估算）；升级前主机应暂停对舵机的轮询，
    否则同总线的舵机读也会超时（`docs/flash_layout.md:538-541`、§10.5）。

13. **boot 模式下遥测窗读回的是 0，不是 IMU 数据。**
    bootloader 没有 256 字节控制表的完整内容（镜像被清零），读 124 会得到 0；判断"在
    bootloader"必须看身份窗 `UID_MODE=1` 或 PING 型号（`src/boot_regs.c:92-110,195-208`；§10.1）。

14. **FeeTech 下写身份窗/升级窗不报错。**
    应用态 FeeTech 写 180..255 是被"接受但忽略"的（§7.4）。主机若在应用态直接写升级窗
    208 会毫无提示地什么也没发生——必须先 `VCMD_BOOT` 进入 boot 模式。

15. **节点寄存器里的固件版本与镜像头版本号不是同一个数。**
    例子：寄存器报 1.0（`0x10`），身份窗/镜像头报 1.2.0。判断"该不该升级"要用身份窗的
    `image_version` + `imgcrc`（`host/upgrade.py:741-771`），不要只比寄存器 6（§13.1）。

### 13.3 主机如何探测能力

* **扩展能力位**：读身份窗偏移 **11**（绝对 191）`UID_INFO_VERSION`。**== 1** 表示偏移
  12..15（`boot_slot / trial_slot / attempts / boot_stay`）有效；老固件为 0，主机应显示
  "unknown"而不是读那 4 个字节（`src/board.h:198-210`；`host/upgrade.py:82-86,437-441`）。
* **模式**：`UID_MODE` = 0/1（应用/bootloader）。
* **是否打包过**：`UID_FLAGS` 的 bit7（`UID_FLAG_NO_HEADER`）。
* **是否 trial**：`UID_FLAGS` 的 bit0（由配置页折算）。
* **升级目标合法性**：`UID_SLOT_RUN` + `UID_TRIAL_SLOT` + `UID_BOOT_STAY`；bootloader 还会用
  `other_bootable` 内部判断（§10.6）。
* **是否支持 `0x8A`（Fast Sync Read）**：**没有能力位**，只能按行为探测——发一条只点名本机的
  `0x8A`（地址 124、长度 12），收到以 `FE` 开头、`LEN = 1 + 1×(12+4) = 17` 的聚合帧即为支持
  （自 2026-09-30 起的固件）。旧固件把 `0x8A` 当未知指令：广播时静默、点名本机时回
  `ERR = 0x40`，所以"收到 `0x40`"和"超时"都表示不支持（`src/dxl2.c:492-497`）。
  **固件版本寄存器（6）仍是 `0x10`**：这次改动没有动 `FW_VERSION_*`，见 §13.1。
