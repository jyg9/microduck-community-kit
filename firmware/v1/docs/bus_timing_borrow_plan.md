## 1. 真机实测（2026-09-23，`/dev/ttyACM1`）

### 1.1 设备与身份

| 项 | 实测值 | 备注 |
|---|---|---|
| 适配器 / 设备 | `1a86:55d3 USB Single Serial`（cdc_acm）→ `/dev/ttyACM1`，权限 0666 | 宿主时间戳受 USB 限制（§1.6） |
| 波特率 | 1 Mbps（寄存器 6 = 0） | 与 `microduck` 的 1 Mbps 一致 |
| ID / 副 ID | **1** / 253（`0xFD`） | 副 ID 出厂是 0xFD（"未设置"），不是"禁止值" |
| 固件 / 端序 / 型号字 | **3.46**（`0x2E03`）/ **0 小端** / `0x1F0A`（10.31） | 对方 §9 要求"放真实版本号"，这就是对照 |
| 应答级别（8） | **1** | 与对方假设一致 |
| 运行模式（33） | **4** | 与对方 §2 的结论一致（不是 0） |
| 锁（55） | **1**（EPROM 写入掉电不保存） | 与我方 `dev.c` 的锁语义实现一致 |
| 最低输入电压 | **40 = 4.0 V**（母线实测 4.4 V） | 4.4 V 是**开发板 USB 供电能力不足**造成的，已知且临时；后续会提高到 7 V 以上，见 §1.7 |

### 1.2 地址 56 的块：12 / 15 / 20 / 21 字节都能读

| 请求长度 | 结果 | 数据（十六进制，56 起） |
|---|---|---|
| 12 | OK status=0 | `0100 0000 0000 2c 1d 00 00 00 01` |
| **15** | **OK status=0** | `0100 0000 0000 2c 1d 00 00 00 01 00 04 00` |
| 20 | OK status=0 | 追加 `00 00 f7 07 05`（= 寄存器 71..75） |
| 21 | OK status=0 | 追加 `3c`（= 寄存器 76） |

**解读**：56..70 的 15 字节是**文档化块**：
`pos(56) speed(58) load(60) volt(62) temp(63) 寄存器64 status(65) moving(66) 位置类(67-68) current(69)`；
再往后（71..76 实测 `0, 2039, 5, 60`）是别的寄存器，不是为外部设备预留的空间。
⇒ 想和舵机**共用同一个读长**，15 是唯一"足够、且对所有型号都成立"的选择（D1）。

### 1.3 位次与应答时序（每例 n = 21，取中位数）

| 用例 | 首字节（ms） | 相对基线 | 完整应答（ms） | 应答的 ID |
|---|---|---|---|---|
| `PING 1` | 0.339 | — | 0.416 | 1 |
| `READ 56/15` | 0.527 | — | 0.759 | 1 |
| `SYNC_READ [1]` | 0.526 | 基线 | 0.775 | [1] |
| `SYNC_READ [7,1]`（前 1 个缺席） | 0.828 | **+0.302** | 1.045 | [1] |
| `SYNC_READ [7,8,1]`（前 2 个缺席） | 1.121 | **+0.595**（+0.297/个） | 1.362 | [1] |
| `SYNC_READ [7,8,9,1]`（前 3 个缺席） | 1.408 | **+0.882**（+0.294/个） | 1.634 | [1] |
| `SYNC_READ [200,1]`（**运行时布局**：IMU 位缺席） | 0.829 | **+0.303** | 1.084 | [1] |
| `SYNC_READ [1,7]`（缺席在后） | 0.549 | +0.023 | 0.776 | [1] |
| `SYNC_READ [1]` 读 20 字节 | 0.606 | +0.080 | 0.894 | [1] |
| `SYNC_READ [7]`（只有缺席） | — | 超时 | — | [] |

**结论（D2 的依据）**：

1. 舵机**按 ID 列表里的位次**推迟应答，**每个前导 ID 占 ≈ 295 µs**，与"该设备在不在线"无关——
   线性度极好（0.302 / 0.297 / 0.294）。
2. 缺席在**后面**不影响（+0.023 ms）；只有前面的 ID 计入。
3. 295 µs ≈ 一个 21 字节应答的线上时间（210 µs）+ ≈85 µs 空隙/T_resp。
   ⇒ 排在后面的设备**只给我们 ≈ 295 µs**：从"指令帧最后一个停止位"到"我们第一字节"必须**紧**。
   这是 D3 硬指标的来源（比对方的"硬上限 100 µs"更贴近真实，但 100 µs 仍是应该守的目标）。
4. 因此**不能**用对方的"总线静默 1 ms 判缺席"：k=1 时应答窗口在 295 µs 就打开了。

### 1.7 `0x08` REBOOT 实测（2026-09-24，用户确认舵机空载可重启）

对方《飞特适配架构》§3.4 说"飞特新固件有 REBOOT（0x08，约 800 ms，先关扭矩）"，
而仓库根 `docs/飞特通讯协议说明.md`（厂商手册）的指令表里**没有 0x08**（依据的是更旧的手册）。
用户允许重启（舵机输出轴没接任何负载），工具 `host/tools/servo_reboot_probe.py` 的实测：

| 项 | 实测 | 说明 |
|---|---|---|
| `0x08` 是否存在 | **存在**（HD-1910-C001，fw 3.46） | 我们的旧手册表缺这一条，需补 |
| 是否应答 | **不应答**（请求超时） | 与手册/对方说法一致 |
| 多久回来 | **823 ms**（PING 每 20 ms 轮询） | 与手册"约 800 ms"一致 |
| ID / 波特率 / 模式 / 锁 / OFS | **全部不变** | EEPROM 设置保留 |
| 扭矩 | 保持关（本来就是关） | 手册要求重启前先关扭矩 |
| RAM 增益 50/51 | 先把 Kp/Kd 写成 **99/88**，重启后回到 **32/40**（= EEPROM 21/22） | 证实"重启后 RAM 回 EEPROM"，正是 `RobotIo::reboot` 契约要求的 |

由此定下 **D9**（见 §0 表）：节点的 FeeTech 人格补上 `0x08`（不应答、走 `dev_request_reboot()`，
应用与 bootloader 共用），主机补丁的 `reboot()` 从"明确不支持"改成"先扭矩 0、发 0x08、不等应答"。

## 2. 用实测常数重算时间预算

槽长实测 ≈ 295 µs（= 21 字节应答 210 µs + ≈85 µs 空隙）。

| 方案 | 一次 16 设备事务（1 指令 + 我们 + 15 舵机） | 结论 |
|---|---|---|
| 共享长度 **15**（选定） | 240 + 210 + 15 × 295 ≈ **4.9 ms** | 6 ms 验收线内，余量 1.1 ms；占 20 ms tick 的 25% |
| 共享长度 20（否掉） | 240 + 260 + 15 × 345 ≈ **5.7 ms** | 只剩 0.3 ms 余量，任何抖动都越线 |

* 对方原估 3.6 ms，**低估约 35%**：它按"210 µs/设备"算，没算设备之间 ≈85 µs 空隙。
  ⇒ 我们的验收线用 **≈4.9 ms / p99 < 6 ms**。
* **我们自己的应答也必须在 295 µs 内起来**，否则第 1 颗舵机就在我们应答中间开口（D3）。
* **追加（2026-09-30，D10）：Dynamixel `0x8A` 的账【推算】** —— 16 台设备各读 12 字节时，聚合帧
  的 `LEN = 1 + 16 × 16 = 257`、整帧 264 字节 ≈ **2.6 ms**（1 Mbps、10 bit/字节），比上表 `0x82`
  的 4.9 ms 省约 2.3 ms：每台少一个 7 字节帧头与一次 ≈85 µs 转向，代价是每段多 2 字节 CRC。
  这条路径与原版 Dynamixel 路线绑定（FeeTech 总线没有 `0x8A`），不影响上面的 FeeTech 预算。

## 4. 实施内容（P0/P1，2026-09-24 已完成）

> 下面每一节先保留当初的"要做什么"，末尾加 **实施结果**，逐条说明落地到了哪个文件、
> 与计划有何偏差。实测数据集中在 §7。

### P0-A · sync_read 位次仲裁（D2）

* **做什么**：`fee.c` / `dxl2.c` 的 `SYNC_READ` 分支不再立即出帧，改为返回"待发 + 位次状态"；
  新增应答调度器（`bus.c` 层或独立 `src/bus_arb.c`）：
  ```
  收到 sync_read 指令帧结束 → 记下自己的下标 k、读长、地址
  对 j = 0..k-1：
      等 (a) 一个完整的、ID 在列表里的应答帧结束（按长度/校验和判定），或
         (b) SLOT_US ≈ 300 µs 超时（缺席设备同样只占一槽）
      出现新的指令帧（FF FF …）→ 本次作废
      累计等待 > 25 ms → 放弃（不应答，计诊断）
  → 交给 P0-B 的发送路径（T_resp ≤ 100 µs 目标）
  ```
* **依据**：§1.3 的线性槽长；对方的"1 ms 静默"在这里是错的。
* **需要**：µs 级时基（DWT 周期计数或自由运行 TIMER；systick 只有 1 ms）。
* **风险**：等在前面时要保持接收；半双工单总线上只收不发是合法的。
* **验证**：把 `servo_probe.py` 的思路扩成"我们的节点 + 真舵机同总线"，
  两种布局都要过：200 在第 0 位（运行时）、不存在的 ID 排在 200 前面。

**实施结果**：`src/bus_arb.c`（纯逻辑，无硬件依赖）+ `bus.c` 的 `bus_emit()`。
`fee.c` / `dxl2.c` 只在 slave 结构里多记两个字段 `sync_named` / `sync_index`（在自己的
`SYNC_READ` 分支里填），不改 `*_slave_feed()` 的签名。**与计划的偏差**：
* 不做"观察前面应答帧结束"的嗅探——实测前导设备**缺席也占一槽**（§1.3），
  等应答帧结束与固定 300 µs 在同一个 `sync_read` 里是同一件事，固定槽更简单也更可测；
* 不做"25 ms 放弃"——槽数是有限的（k ≤ 250），等待天然有界；
* 取消等待的条件是"出现新的指令帧（本机 ID 或广播）"，由一个 3 字节小状态机判断
  （FeeTech 第 3 字节是 ID，DXL 第 3 字节是 `0xFD`、ID 在第 5 字节），见 `bus_arb_rx()`。
  在真机上用"前导 ID 缺席"的方式验证了线性槽长（§7）。

### P0-B · 硬实时应答路径 + 原子快照 + 回声窗口（D3 + D4）

* **做什么**：
  1. 帧结束判定放进 USART 中断（现在只把字节塞进环）；
  2. 组帧（≤ 31 字节）后用 **DMA 发送**（GD32F303 有 DMA，本工程目前完全没用），CPU 立即返回；
     发送完成中断里清标志/开回声门；
  3. 遥测快照：主循环发布 `telem_snapshot_t`（12 字节数据 + 计数 + 状态位 + 加速度 + 版本），
     中断侧只做定长拷贝；`dev_refresh()` 不再出现在读路径，ADC/浮点/`vendor_sync` 全部移出；
  4. 回声：`uart_port` 的回声门从"发送后 2 ms"改成"TX 忙期间 + 2 字节时间（≈20 µs）"，
     保留 `echoed` 计数用于确认窗口。
* **指标**：T_resp 目标 ≤ 100 µs、**硬上限 < 250 µs**（实测余量 ≈295 µs）。
* **风险**：DMA 与逐字节 RX 中断共存要小心（TX/RX 分通道）；ISR 里组帧只能用静态缓冲，
  不能再进 `dev_read` 的"每次刷新"路径；RX 环 256 B 与突发 315 B 的耦合（收紧回声门后
  15 颗舵机的应答会进环 ⇒ 主循环单次迭代必须 < 环一半 ≈1.28 ms）。
* **验证**：示波器/逻辑分析仪量 T_resp 直方图；P0-A 的同总线测试；连续 1000 次背靠背读 0 丢失。

**实施结果**：
* `uart_port.{h,c}` 不再有 RX 环形缓冲：中断收字节 → `on_byte(index, byte)` 回调 → `bus.c`
  里跑协议状态机；TX 改成 `uart_port_write_dma()`（USART0_TX = DMA0 CH3、USART1_TX = DMA0 CH6，
  取自 GD32F30x 用户手册图 10-4，并用真机验证），`DMA0_Channel3/6_IRQHandler` 在 `gd32f30x_it.c`；
* 每个端口一份应答缓冲 + 一份延迟缓冲（512 B each，RAM 因此 +1 KB）；
* 遥测发布：`dev_refresh()` 只在主循环调用（`main.c` 里"新样本或 50 ms"触发），
  用 `src/critical.h` 的 `irq_save/irq_restore` 包住几十字节的发布；`dev_read()` 不再刷新；
* 在 `uart_port_write()`（调试口）的字节循环里逐字节检查 `tx_busy`：开发板上调试口与总线
  共用 USART0，日志行必须在字节边界给协议帧让路——**这是真机跑冒烟时才暴露的**，
  最初只是"整行前检查一次"，一行 100 字节写到一半就会被协议帧插进来；
* 回声门最后落成**时间锚定窗口**而不是固定字节数：`uart_port_tx_complete()` 只设置
  `echo_until_us = us_now() + echo_window_us(baud)`（3 个字节时间，1 Mbps 下 ≈30 µs），
  `uart_port_isr()` 用 `tx_busy || (int32_t)(echo_until_us - us_now()) > 0` 丢弃自收字节。
  固定 2 字节在真 PCBA 上会吃掉下一帧帧头，见 §4.6.1；
* `main.c` 增加主循环迭代时长的**高水位统计**（`loop_max`），在统计行里打印；
* **偏差**：`dev_temp_celsius()` 仍保留在 `dev_refresh()` 里（1 Hz 限频 + 在临界区之外读），
  没有单独搬走。

#### 4.6.1 `echo_skip` 吃掉下一帧帧头（`src/uart_port.c`）

* **现象**：每两次事务只成功一次。`frames` = 200 次请求里 100；`rx_bytes` = 1600 B = 200×8，
  即每个请求都到了 USART，但一半从未被组帧。2 ms 间隔下 50/100/50/100 ok/timeout；
  20 ms 间隔下 50/50（所以不是总线碰撞）；每个请求前加 2 个哑字节时 100/0。
* **根因**：`uart_port_tx_complete()` 在 DMA 发送完成时固定设置 `echo_skip = 2` 字节，
  假设半双工收发器会把我们自己的应答回灌。这块 PCBA 的收发器**不回灌**，于是这 2 字节
  跳过一直留着，把**下一个请求帧的 `FF FF` 吃掉**。
* **修复**：把"固定字节数"换成**时间锚定的窗口** `UART_ECHO_WINDOW_BYTES`
  （3 个字节时间，1 Mbps 下 ≈30 µs，按波特率算）：`uart_port_tx_complete()` 只设置
  `echo_until_us = us_now() + echo_window_us(p->baud)`，`uart_port_isr()` 用
  `tx_busy || (int32_t)(echo_until_us - us_now()) > 0` 丢弃自收字节（`src/uart_port.c`）。
  时间窗口不可能吃掉合法帧头——最早的合法流量约 85 µs 之后，主机下一条指令是毫秒级。
* **实测证据（修复后）**：400/400 次应答；节点侧 `rx=3200 frames=400 answered=400
  tx=8400 echo=0`。

#### 4.6.2 `us_now()` 每 35.8 s 回绕，所有期限失效（`src/us_time.c`）

* **现象**：节点在一次运行中途**静默**，但传感器仍报健康——
  `uart1 rx=1396097 echo=710906 frames=29758 answered=1747`，`frames`/`answered` 冻结，
  而 `echo` 以恰好等于接收速率的速度增长（每个字节都被当成回声丢弃），
  `loop_max=4259175904us`。
* **根因**：`us_now()` 返回 `DWT->CYCCNT / cycles_per_us`。CYCCNT 在 2^32 个周期
  （120 MHz 下 35.8 s）回绕，于是微秒值每 35.8 s 掉回 0，而不是按 2^32 µs 回绕；
  `(int32_t)(deadline - us_now()) > 0` 这类判据每次回绕后都会误判一次。
* **修复**：`us_time_tick()` 由 SysTick 处理函数每毫秒调用一次并重新锁存 CYCCNT
  （`src/gd32f30x_it.c` 的 `SysTick_Handler()`）；`us_now()` 返回
  `ms * 1000 + (CYCCNT - latch) / cycles_per_us`，亚毫秒部分钳到 999，于是它是真正的
  modulo-2^32 微秒计数器（回绕 71.6 min），且 `(ms, latch)` 这一对在短临界区内读取
  （`src/us_time.c`）。
* **实测证据（修复后）**：重 `sync_read` 流量下 `echo=0`；同一次运行的 `loop_max` 变成
  正常的 6 ms（台架构型下调试口与总线共用 USART0，这 6 ms 是调试口那条阻塞的统计行）。
* **连带解释**：`robotd` 此前"打开端口后第一次 `sync_read` 就缺 id 200"以及间歇的
  "4 次 stale 读"，根因都是这个时钟；时钟修好后 `robotd` **第一次**就绑上了总线。

#### 4.6.3 SFLP 重启发布未收敛姿态（`src/imu_spi.c`）

* **现象**：SFLP 重启后"融合重新收敛前四元数字节为零"的文档契约失效：`VCMD_RESET_SIM`
  之后四元数在 2.5 s 内从未归零（第一次非零在 2 ms）。
* **根因**：`imu_spi_restart()` 只把六个四元数字节清零一次，但芯片在 `SFLP_GAME_INIT`
  脉冲期间**继续输出格式良好的 SFLP 字**（实测 `sflp_words` 以约 115.5/s 持续增长、
  重启期间无停顿），下一次 `imu_spi_step()` 在 `dev_refresh()` 发布之前就把零覆盖了。
* **修复**：`src/imu_spi.c` 新增 **CONVERGE 状态**：重启后（以及初始化后）驱动丢弃 SFLP 字，
  发布零四元数字节并清 `TELEM_FLAG_SFLP_VALID`，持续 `LSM_SFLP_CONVERGE_MS` = 1500 ms
  （数据手册 0.8 s 校准 + 0.7 s 稳定，`src/lsm6dsv16x.h`），然后 flush FIFO 再恢复发布
  （`imu_spi_begin_converge()` / `imu_spi_end_converge()` / `imu_spi_step()`）。
* **实测证据**：两条 SFLP 重启冒烟检查现在通过——"VCMD_RESET_SIM zeroes the quaternion"
  在 **9–13 ms** 后归零；"SFLP 在重启后 **1.51–1.52 s** 恢复非零（< 2.5 s）"。
* **附带：FIFO tag 编码（排查时踩的坑）**。`TAG_SENSOR[4:0]` 是 tag 字节的 bit 7:3，
  `TAG_CNT` 在 bit 2:1，所以 game rotation vector 的原始字节是 `0x13 << 3` = `0x98`
  （实际读到 `0x98/0x9A/0x9C/0x9E`）。拿字节直接和 `0x13` 比较**什么也匹配不到**——
  这浪费了一轮调试，现在由 `src/lsm6dsv16x.h` 的 `LSM_TAG_SENSOR()` 和
  `host/tools/test_protocols.c` 的 `test_lsm_fifo_tag()` 钉住。

* **每笔事务多付一次 `tcdrain`**：`serialport` 的 `flush()` 实测固定 **~12 ms**（8/9/24/56 字节、

* **`BURST_IDLE` 2 ms → 4 ms**：实测 13.5 万个相邻应答间隔 median 0.27 / p99 0.57 / **max 1.94 ms**，

改完同一块板子上是 **50.0 Hz / missed 0**。**残留**的孤立掉读（每 5 分钟窗口 0–3 次，≈1/15000
tick）**不是**尾巴型截断：2026-10-02 的 journal 里每一条都是 `id(s) … missing`（没有一条是
`faulted status`），缺失集合是**散的**（例如 `200,22`、`31,34`、`23,31`、`33,11`），而尾巴型截断
只会砍掉到达顺序的**一段后缀**——`200` 是第 0 槽、`22` 是第 3 槽，不可能是"最后才该到"的。
所以机制在驱动/舵机一侧，与这个判据无关，也没有再动它。本节与
`docs/imu_to_dxl_protocol.md` §12 第 8 项记录的是同一次测量。

| 场景 | 结果 |
|---|---|
| 本节点在第 0 位（microduck 的 tick 读，`[200] + 15 关节`） | 应答 24 字节：`FE`、`LEN = 257`、`ERR = 0`、`ID = 200`、累积 CRC 正确；补上 15 段合成舵机段后整包 264 字节，`host/bus.py` 的参考解析器（照 rustypot 1.8 抄写）逐段校验通过，第 0 段就是本节点的 12 字节遥测（**不填充**：数据里带 `FF FF FD` 也原样发出） |
| 本节点在第 1 位（`[10, 200, 11]`，主机扮演 0 号设备发前缀+块） | 收满 24 字节后立刻发自己那 16 字节块（无前缀、无 error），补上第 2 段后整包 3 段解析通过 |
| 未被点名 / 前缀不对 | 静默（负例：只发块不发前缀，节点拒绝——`ignored` 计数 +1） |
| `0x8A` 与 `0x82` 同一采样 | 状态位一致、采样计数一致，计数未动时**字节完全相同** |
| 20 次背靠背读 | 0 丢失 |

**由此揪出的缺陷（重要，与 `0x8A` 无关的固件 bug）**：中间位置一开始**必失败**——节点收到
指令后从来不回应答，`ignored` 计数不变、`gaps` 也不变。用调试口逐位计数定位后确认：**USART1
的接收中断里解析完一整帧所需的时间超过了 1 Mbps 下一个字节的 10 µs，紧跟其后的字节被
USART 的单字节接收寄存器覆盖丢掉**（`rx_bytes` 比主机写入的字节数少 1 就是直接证据；
`rx_errors` 一直是 0，因为 ORERR 已被字节循环里那次读 DATA 清掉了——这也是一个统计盲点）。

* 根因是 **按位实现的 CRC-16**：`crc16_dxl(f, total-2)` 对 15..28 字节的指令帧要
  ≈1300..2400 个循环迭代，在 120 MHz 上约 **11..20 µs**，单这一项就超了一个字节时间。
* 处置：`src/crc16.c` 改成 **256 项查表**（多 512 B flash），`crc16_dxl_update` 降到约 5 个周期
  一次；所有向量（`host/tools/test_crc16.c` 的 rustypot/ROBOTIS 向量、协议测试、与真 rustypot
  的对拍）不变。改完 `rx` 增量与主机写入字节数**逐字节相符**，中间位置随即全过。
* 这条对整条总线都有意义：**任何一台"紧跟指令帧发言"的设备都会被吃掉首字节**。原来没暴露，
  是因为运行时把本节点放在第 0 位（它自己就是第一个发言的），而 §7.3 的延迟路径测量里前导
  ID 全是缺席设备（总线安静）。`0x8A` 是第一条要求"别人先说话、我们后说话"的指令。
* 顺带把 `dxl_slave_reset()` 的语义收紧了：`0x8A` 的聚合帧在**第一个字节到达之前**的间隔
  不再作废应答（前导设备允许有自己的 `return_delay_time`，出厂值 250 ⇒ 500 µs > `BUS_GAP_US`），
  但**流一旦开始**再断掉仍然作废——否则一段属于"不存在的包"的块会晚到地插入别人的事务。
  两条都有宿主测试钉住（`test_protocols.c`）。

资源占用（Release，`IMU_USE_SPI=1`，`arm-none-eabi-size`）：应用镜像 **25528 + 124 B / 254 KB**、
`RAM 8724 + 188 B (18.2%)`；slot 镜像 26028 + 188 B（26.7%）；bootloader **20200 + 116 B (62.1%)**
——比 §7.5 那一轮各多约 0.5 KB flash，全部是 CRC 表（512 B）。
